## 3. Целевая архитектура

```
┌────────────── Electron ──────────────┐        ┌───────── FastAPI ─────────┐
│ React (renderer)                     │        │                          │
│   │  IPC (preload contextBridge)     │        │  PostgreSQL + Redis      │
│   ▼                                  │  HTTPS │                          │
│ SQLite (main process, WAL)           │◀──────▶│  REST + WebSocket        │
│   • кэш меню/залов/сотрудников       │        │  /health, /sync/*, /pos  │
│   • локальные заказы и оплаты        │        └──────────────────────────┘
│   • outbox (очередь операций)        │
│   • dead-letter                      │
│        ▲                             │
│ Sync Engine (main): ping 10 с,       │
│ отправка outbox, pull изменений      │
└──────────────┬───────────────────────┘
               │ локальная сеть, порт 8765
        планшеты официантов / KDS / раздача
```

Принцип: **UI всегда читает и пишет локально**, сеть — фоновый транспорт. Ошибка сети
не меняет поведение экрана, только индикатор.

## 4. Локальная БД

Файл в `app.getPath('userData')/marjon.sqlite`, режим WAL, доступ только из main-процесса
через IPC. `localStorage` для денежных данных не используется.

Таблицы:

- `cache_categories`, `cache_products`, `cache_halls`, `cache_tables`,
  `cache_printers`, `cache_templates`, `cache_settings` — снимки справочников.
- `cache_staff` — id, имя, роль, `permissions`, `pin_hash` (bcrypt), `pin_updated_at`,
  `is_active`. Только хэши, никогда открытый PIN.
- `orders_local`, `order_items_local`, `payments_local`, `shifts_local` — рабочие данные
  смены; `local_number`, `client_id`, `sync_state`, `server_id`.
- `outbox` — `id, seq, entity, entity_id, op, method, path, body, idempotency_key,
  depends_on, state (pending|sent|failed|dead), attempts, next_attempt_at, last_error,
  created_at, synced_at`.
- `sync_meta` — курсоры `since` по сущностям, версия bootstrap, время последней связи.
- `print_jobs_local` — локальные задания печати и их подтверждение.
- `audit_local` — расхождения цен, повторные входы, отказы синхронизации.

Ничего не удаляется физически: только статусы и архивация по закрытию смены.

## 5. Синхронизация

### 5.1. Очередь и порядок

1. Каждая мутация сначала пишется в локальные таблицы и в `outbox` одной транзакцией.
2. `depends_on` задаёт порядок: позиции не уходят, пока не подтверждён заказ;
   оплата не уходит, пока не подтверждены позиции; статус — после оплаты.
3. Отправка FIFO с экспоненциальным backoff (2, 5, 15, 60 с), максимум попыток —
   затем `dead` и запись в экран «Несинхронизированное».
4. Серверный 4xx (кроме 401/403/429) — сразу `dead`, повторов нет: это конфликт данных,
   а не сеть. 401 — обновление токена, 5xx/таймаут — повтор.

### 5.2. Идемпотентность

- Клиент генерирует `client_id` (UUIDv4) при создании заказа и `Idempotency-Key` для
  каждой мутации.
- Бэкенд: `Order.client_id` (nullable) + уникальный индекс `(company_id, client_id)`.
  Повторный `POST` возвращает существующий заказ с `200`, а не создаёт дубль.
- Тот же принцип для оплат — заголовок уже поддержан, добавить `client_id` в тело.

### 5.3. Нумерация

- Локальный номер: `{код терминала}-{YYMMDD}-{SEQ}`, например `T1-261113-007`,
  счётчик хранится в `sync_meta` и не сбрасывается при перезапуске.
- Сервер сохраняет его как `client_number` и присваивает канонические `order_number`
  и `public_id` при синхронизации. В отчётах — серверный номер, в чеке офлайн — локальный
  с пометкой «офлайн».

### 5.4. Цены и состав

- Клиент отправляет `unit_price` из снимка меню и `price_snapshot: true`.
- Сервер при `client_id` + офлайн-метке доверяет цене продажи и пишет расхождение
  с текущим меню в аудит. Пересчёт «по-своему» запрещён: чек уже напечатан.

### 5.5. Загрузка данных

- `GET /sync/bootstrap?branch_id=…` — меню, категории, залы, столы, принтеры, шаблоны,
  настройки, стоп-лист; вызывается при старте и раз в 30 минут онлайн.
- `GET /sync/changes?since=…&branch_id=…` — дельты заказов, смен, стоп-листа.
- Персональные данные сотрудников — отдельный endpoint под токеном моноблока
  (`GET /sync/staff?branch_id=…`), с `Cache-Control: no-store` и отзывом при увольнении.

### 5.6. Конфликты

| Ситуация | Правило |
|---|---|
| Статус изменён офлайн, заказ отменён на сервере | Server wins + уведомление кассиру/повару |
| Два терминала офлайн открыли один стол | Оба заказа сохраняются, второй «требует внимания», объединение вручную |
| Цена изменилась за время офлайна | Действует цена продажи, расхождение — в аудит |
| Стоп-лист изменился | После синхронизации обновить кэш и показать уведомление |
| Повторная отправка после таймаута | `client_id` исключает дубль |

## 6. Офлайн-сценарии по поверхностям

- **Касса.** Полный цикл: открыть заказ → позиции → пречек → наличные → закрыть стол.
  Смена открывается локально и уходит в очередь. Закрытие смены и Z-отчёт — онлайн
  (решение по офлайн-закрытию — в открытых вопросах).
- **Чек.** Онлайн — как сейчас, серверное задание. Офлайн — локальная сборка ESC/POS
  из кэшированного шаблона и печать через `window.electron.print`; после синхронизации
  подтверждение задания, чтобы сервер не напечатал повторно.
- **PIN.** Локальная проверка по bcrypt-хэшу, TTL кэша 14 дней, обновление при каждом
  успешном подключении, локальный счётчик неудач и блокировка.
- **KDS и раздача.** Остаются на последних данных с индикатором; смены статусов уже
  в очереди. Новые офлайн-заказы кассы до них доходят только через мастер-терминал
  (этап 6).
- **Планшеты официантов.** Через локальный прокси 8765 мастер-терминала: касса отвечает
  из своей SQLite и складывает операции в тот же outbox. Удалённый телефон вне Wi-Fi
  увидит данные только после выхода кассы в интернет.
- **Веб-панель.** Только онлайн: баннер «нет связи», сохранение блокируется,
  после восстановления — автоматический refresh (как в дополнении к ТЗ).
- **Гостевой ТВ.** Облачный, офлайн — «нет связи — последние данные».

## 7. Изменения бэкенда

1. Миграция `orders`: `client_id`, `client_number`, `created_offline_at`,
   `synced_at`; уникальный индекс `(company_id, client_id)`.
2. `POST /pos/orders`: принимать `client_id`, `client_number`, `price_snapshot`;
   повтор возвращает существующий заказ.
3. `POST /pos/payments`: `client_id` в теле; офлайн-импорт наличных с флагом
   `offline_import`; карта/провайдеры — 409 при офлайне.
4. `GET /sync/bootstrap`, `GET /sync/changes`, `GET /sync/staff`.
5. `OfflineJob`: либо реализовать обработчик, либо не использовать как транспорт.
   Решение: outbox живёт на клиенте, `OfflineJob` оставить для мобильных клиентов
   и реализовать обработчик отдельной задачей.
6. Аудит: расхождение цен, офлайн-продажи, поздняя синхронизация, повторные входы.
7. Фискализация: офлайн-продажи попадают в существующий fiscal outbox после синка;
   API отдаёт возраст самой старой нефискализированной продажи.

## 8. Этапы

### Этап 0 — подготовка (0,5–1 день)
- Копия `dev.db`, ветка `feat/offline-sync` от `main`, вливание через PR
  (`docs/ONBOARDING.md` §16), фиксация текущих тестов.
- Решения по открытым вопросам (§10) до начала кодирования.

### Этап 1 — SQLite и кэш (3–5 дней)
- `better-sqlite3` в main, схема, миграции, IPC через preload.
- Перенос кэша GET из `localStorage` в SQLite; bootstrap при старте.
- Критерий: при выключенном сервере касса открывает меню, залы и сотрудников из SQLite.

### Этап 2 — outbox и идемпотентность (4–6 дней)
- Таблица outbox, движок отправки, backoff, dead-letter.
- Миграция `client_id` и идемпотентный `POST /pos/orders`.
- Индикатор связи: `/health` раз в 10 с + WS, три состояния.
- Критерий: повторная отправка одного заказа после таймаута не создаёт дубль (pytest).

### Этап 3 — офлайн-цикл заказа (5–7 дней)
- Заказ, дозаказ, удаление позиции, перенос, смена официанта, наличная оплата.
- Локальная нумерация, снимок цен, открытие смены.
- Экран «Несинхронизированное», повтор и сброс (по праву).
- Критерий: 2 часа без сети → 30 заказов и оплат → синк → в отчётах ровно 30,
  суммы совпадают, дублей нет.

### Этап 4 — локальная печать (3–4 дня)
- Сборка ESC/POS в терминале, кэш шаблонов, пречек, повтор чека.
- Подтверждение локально напечатанных заданий после синка.
- Критерий: чек печатается без сервера, после синка сервер не печатает повторно.

### Этап 5 — офлайн-вход (2–3 дня)
- `GET /sync/staff`, кэш хэшей и прав, TTL, локальная блокировка.
- Критерий: перезапуск кассы без сети → вход по PIN работает, права совпадают.

### Этап 6 — мастер-терминал (3–5 дней, только при планшетах/KDS в зале)
- Локальный режим порта 8765: ответы из SQLite, локальный WS, общий outbox.
- Критерий: планшет в той же Wi-Fi создаёт заказ без интернета, KDS видит его локально.

### Этап 7 — мобильное приложение (отдельный поток, 4–6 дней)
- Flutter: локальный кэш (sqflite) и своя очередь; синхронизация через тот же API.
- Делать после десктопа: правила идемпотентности будут готовы.

### Этап 8 — выпуск (2–3 дня)
- Бэкап локальной БД, диагностика, предупреждение о возрасте офлайн-буфера.
- Обновление десктопа: `electron-updater` уже вызывается, но `publish` в
  `desktop/package.json` ведёт на чужой репозиторий. Либо починить владельца/канал
  релизов, либо честно оставить ручную установку и описать её клиенту.

Итого: **~5–6 недель** на десктоп целиком (этапы 0–5, 8), без мастер-терминала
и мобильного клиента.

## 9. Тестирование

- **pytest:** идемпотентный повтор заказа и оплаты, `client_id`, права `/sync/staff`,
  офлайн-импорт наличных, аудит расхождений.
- **vitest:** outbox (FIFO, `depends_on`, backoff, dead-letter), слияние дельт,
  локальная нумерация.
- **E2E (Playwright + Electron):** гасим сервер → заказ → наличные → перезапуск
  приложения → поднимаем сервер → ровно один заказ в БД и отчёте.
- **Ручной сценарий:** firewall-блок API на 2 часа, 30 заказов, сверка сумм и чеков.
- **Нагрузка:** 200 офлайн-операций в очереди, отправка батчем, отклик UI без просадок.

## 10. Риски и открытые вопросы

| Риск | Решение |
|---|---|
| Деньги в localStorage теряются по квоте | SQLite с транзакциями и WAL |
| Дубли после таймаута | `client_id` + уникальный индекс |
| Разные цены в чеке и на сервере | Снимок цены на продаже + аудит |
| Часы терминала сбиты | Порядок по `seq`, время — серверное при синке |
| Офлайн-буфер нарушает срок ОФД | Предупреждение по возрасту, лимит согласовать с ОФД |
| Нет автообновления десктопа | Ручная установка; учесть в инструкции клиенту |
| Релиз собран с `.env.development` (`VITE_DEFAULT_SERVER_URL=localhost`) | Перед сборкой проверять `.env.production`; шаг в чек-лист выпуска (этап 8, `ONBOARDING.md` §18) |

## 11. Что осознанно не делаем

- Склад, финансы, отчёты, Z-отчёт, управление сотрудниками — только онлайн.
- Карта, Payme, Click, Uzum — только онлайн.
- Автоматическое объединение заказов на одном столе — запрещено, только вручную.
- Полный офлайн веб-панели — не требуется (дополнение к ТЗ: онлайн-only).

## 12. Что уже реализовано (2026-11-14)

### Бэкенд

- `POST /pos/orders` идемпотентен по `client_id` (частичный уникальный индекс);
  повтор возвращает 200 и тот же заказ.
- `price_snapshot` + `offline_totals` + `created_offline_at`: сервер проверяет
  арифметику снимка и пишет аудит `order.price_snapshot_mismatch`.
- `POST /payments` принимает `offline_import` только для наличных (карта → 422),
  сохраняет `provider_data.offline_import` и `client_created_at`.
- `GET /sync/bootstrap` — снимок компании/филиала/категорий/продуктов/залов/
  принтеров для локальной SQLite одного филиала.
- `GET /sync/changes` — дельты по `updated_at` с курсором; при `since=None`
  заказы НЕ отдаются (первый опрос только ставит курсор, локальная база не
  забивается старой историей).
- `GET /sync/staff` — bcrypt-хэши PIN и права для офлайн-входа.

### Десктоп (Electron main)

- `electron/offline/db.js` — SQLite (`userData/offline/marjon-offline.db`, WAL):
  `kv`, `orders_local`, `outbox`, `print_jobs_local`, `audit_local`.
- `electron/offline/index.js` — движок: bootstrap/changes/staff, локальные
  заказы и правки, пересчёт сумм в целых копейках по правилам бэкенда,
  локальная нумерация `T?-YYMMDD-NNN`, outbox с `depends_on`, экспоненциальным
  backoff и dead-letter, PIN по bcrypt с блокировкой 5 попыток/60 с, смены,
  локальная печать ESC/POS.
- `electron/offline/http.js` — HTTP без зависимости от axios (таймауты, `NetworkError`).
- `electron/offline/escpos.js` — CP866-чек и кухонный тикет: кириллица, «№»,
  типографика → ASCII (не `?`), переносы по колонкам, отрезка.
- IPC-каналы `offline:*`, проброс в `preload.js` (`window.electron.offline`),
  инициализация в `main.js`, периодическая досылка каждые 20 с.

### Десктоп (renderer)

- `shared/api.js`: сеть всегда первая; при сетевой ошибке запрос уходит в мост:
  заказы (создание с `client_id`, список/получение, дозаказ, кол-во, удаление,
  правка официанта/скидки/стола/примечания, отмена, статус, оплата наличными,
  платежи по заказу), смены (текущая/открыть/закрыть,
  сводка профиля из локальной базы), меню/категории/залы/принтеры (кэш),
  PIN-вход и `/me` по `offline:<id>`, локальная печать чека/тикета.
  При обрыве посреди оплаты серверная попытка снимается, платёж фиксируется
  локально и досылается с `Idempotency-Key`.
- Правки заказа без сети: официант, скидка, перенос стола, примечание, гости
  пересчитывают итог локально; для синхронизированного заказа в очередь ставится
  `order_update` (`PATCH /pos/orders/{id}`), для локального — уходят вместе с
  `order_create`.
- Отмена без сети: заказ, который ещё не покидал терминал, отменяется локально
  (очередь заказа снимается, `sync_state = local`); уже принятый сервером заказ
  без связи не отменяется — пароль отмены компании на терминале не хранится,
  кассир получает понятную ошибку «восстановите соединение».
- Индикатор в шапке: «Офлайн» / «Записей ждут синхронизации: N» /
  «Не отправлено: N» (последнее — dead-letter, с текстом ошибки в title).

### Тесты и проверки

- `desktop/scripts/offline-escpos.test.mjs` — 7 тестов: CP866, типографика,
  отменённые блюда, ширина 58/80 мм, кухонный тикет (`npm run test:offline`).
- `backend/tests/test_offline_sync.py` — идемпотентность, снимок цены, офлайн-оплата
  только наличными, bootstrap/changes, `offline_totals`, `since=None`, `/sync/staff`.

## 13. Сквозная проверка офлайн-цикла (2026-11-14)

`desktop/scripts/offline-sync.e2e.mjs` (`npm run test:offline:e2e`) гоняет
настоящий движок main-процесса (Node-режим Electron, `better-sqlite3` под его ABI)
против изолированного бэкенда на `127.0.0.1:8001` и временной SQLite терминала:

1. bootstrap при живой сети (меню, персонал, принтеры);
2. `apiBase` переключается на мёртвый порт — сеть «пропала»;
3. создаётся заказ на 2 позиции, итог сверяется с ценами меню;
4. наличная оплата фиксируется локально (`sync_state = pending`);
5. чек печатается локально: TCP-«принтер» получает ESC/POS с `ESC @` и отрезкой;
6. очередь показывает `pending >= 2`, `dead = 0`;
7. сеть возвращается — flush отправляет всё, очередь пустеет;
8. в базе сервера ровно один заказ на `client_id`, ровно одна оплата, итог совпадает;
9. повторный flush ничего не дублирует;
10. заказ возвращается из `/sync/changes`, локальная запись помнит `client_id`
    и офлайн-номер;
11. `/reports/orders` показывает одну продажу с `payment_methods = ["cash"]`;
12. правки без сети (скидка 5.00, стол, официант, примечание) уменьшают итог
    локально и после flush доезжают до сервера;
13. заказ, не покидавший терминал, отменяется без сети: очередь заказа
    снимается, `sync_state = local`, после возврата связи на сервере его нет;
14. отмена уже синхронизированного заказа без связи отклоняется понятной
    ошибкой и не меняет статус заказа.

Найденные и исправленные этим прогоном дефекты движка:

- офлайн-платёж отправлял `cash_amount` без `card_amount` — бэкенд отвечал 422
  и операция уходила в dead-letter; теперь отправляются только `amount`,
  `method`, `cash_received`, `offline_import`, `client_created_at`;
- серверный DTO не содержит офлайн-метаданных, и после синхронизации локальная
  запись теряла `client_id`/`client_number` (её больше не находили поиск и
  повторная печать). `applyServerOrder`/`upsertRemoteOrder` теперь сохраняют
  `client_id`, `client_number`, `created_offline_at`, `service_fee_rate`.

Запуск E2E требует поднятого изолированного бэкенда (юнит-проверки
`test:offline`/`test:payments` и сборка от него не зависят):

```bash
cd backend
export DATABASE_URL="sqlite+aiosqlite:///./dev-offline-e2e.db" SECRET_KEY=dev-only-insecure-secret-key
python -c "import asyncio,seed; from app.infrastructure.database.session import create_tables; asyncio.run(create_tables()); asyncio.run(seed.seed())"  # один раз
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001 --lifespan off
# в другом терминале:
cd desktop && npm run test:offline:e2e
```
