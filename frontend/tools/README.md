# Инструменты CSS: проверка внешнего вида и аудит

## Зачем это

В проекте было 11 990 `!important` — не потому, что кто-то писал плохо, а потому
что не было способа проверить правку CSS иначе как глазами. Каждый следующий
разработчик добавлял флаг, потому что боялся сломать невидимое.

Теперь способ есть. Проверка считает **эффективный стиль каждого элемента** на
реальном DOM приложения и сравнивает с эталоном. Скриншоты не используются:
сравниваются вычисленные стили, поэтому результат не зависит от шрифтов,
окружения и версии браузера.

---

## Повседневное использование

```bash
cd frontend

npm run css:verify     # не изменился ли внешний вид
npm run css:baseline   # изменение намеренное — обновить эталон
```

`css:verify` занимает ~2 минуты и делает три вещи:

1. рендерит 55 страниц кафе и 38 разделов админки в jsdom;
2. считает победителя каскада для каждого элемента на 390, 768, 1280 и 1440 px;
3. сверяет с `tools/baseline/*.json` и проверяет отсутствие `!important`.

Тот же скрипт запускается в CI на каждый pull request с правками во `frontend/src`.

### Если проверка не прошла

```
✗ dashboard: 3 элементов
      aside.dashboard-sidebar [#5]
      div.kpi-value [#577]
```

Посмотреть, какое правило победило и почему:

```bash
node tools/explain.mjs .cssaudit/rules-kafe.json .cssaudit/dom dashboard aside.dashboard-sidebar background 1440
```

Выведет всех кандидатов с их слоем, специфичностью и порядком; побеждает
последний в списке.

**Изменение намеренное?** Обнови эталон в том же PR: `npm run css:baseline`,
затем закоммить `tools/baseline/`. Ревьюеру будет видно, что вид менялся
сознательно.

## Как устроены стили

`!important` в проекте запрещён. Приоритет задаётся каскадными слоями:

```css
@layer marjon-base, marjon-important;
```

Слой в каскаде стоит **выше специфичности**: правило из `marjon-important`
побеждает правило из `marjon-base` независимо от веса селектора. Это ровно то
поведение, ради которого раньше ставили флаг, но выраженное явно.

`marjon-important` — это технический долг в рамке. Он постепенно разбирается по
компонентам, каждый перенос проверяется на 1:1. Новый код пишите в
`marjon-base`; если правило не побеждает — это сигнал разобраться со
специфичностью, а не поднять приоритет.

## Состав

| Файл | Что делает |
|---|---|
| `css-verify.sh` | Точка входа: снять DOM → разобрать CSS → сверить |
| `visual-baseline.mjs` | Снимок и сверка эффективных стилей |
| `no-important.py` | Запрет `!important` (парсером, а не поиском по тексту) |
| `explain.mjs` | Кто победил каскад для элемента и свойства |
| `cssx.py` | Парсер CSS с точными байтовыми смещениями |
| `export_rules.py` | Выгрузка правил в JSON для расчёта каскада |
| `cascade.mjs` | Движок каскада: важность → слой → специфичность → порядок |
| `audit/harvest-*.jsx` | Снятие DOM, в том числе в состояниях (свёрнутый сайдбар и др.) |

Инструменты рефакторинга, нужны при разборе слоя:

| Файл | Что делает |
|---|---|
| `find-never-wins.mjs` | Декларации, не выигрывающие каскад нигде |
| `prune_dead.py` | Удаляет их, если мертвы во всех селекторах правила |
| `split-dead.py` | Расщепляет правила со смешанными селекторами |
| `simulate-move.mjs` | Прикидка переноса между слоями без правки файлов |
| `check-inline.mjs` | Конфликты инлайновых стилей со слоями |
| `layerize.py` · `verify-layers.py` | Разложение по слоям и доказательство эквивалентности |
| `baseline_wide.sh` | Сверка с произвольным git-ref (для больших рефакторингов) |

Промежуточные файлы складываются в `.cssaudit/` и в git не попадают.

## Границы применимости

Проверка сравнивает **вычисленные стили**, а не картинку. Она не увидит:

- изменения из-за псевдоклассов `:hover`, `:focus`, `:active` — jsdom их не
  вычисляет; классы-состояния (`.is-collapsed`, `.is-open`) сняты отдельными
  вариантами DOM и проверяются;
- псевдоэлементы `::before` / `::after` — их нет в `querySelectorAll`;
- элементы, не встречающиеся ни на одной из снятых страниц.

Это не повод не доверять зелёному результату — но при крупном рефакторинге
сайдбара или модалок стоит дополнительно посмотреть глазами.

## Известные находки

Оставлено как есть, требует отдельного решения:

- `.marjon-owner-dashboard` — целая ветка легаси-стилей, класса нет ни на одной
  странице. Кандидат на удаление.
- `border-radius` у похожих элементов гуляет между 8, 9, 12 и 13 px — след
  слоёв патчей. Выровнять — значит сознательно изменить внешний вид, это
  решение дизайнера, а не рефакторинга.
