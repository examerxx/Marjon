## 1. Анализ рынка и боли клиентов

### 1.1. Рынок HoReCa Узбекистана

| Показатель | Значение |
|-----------|----------|
| Население | 37 млн человек |
| Потребители общепита (2024) | ~29 млн (+61% за 4 года) |
| Рост числа заведений (6 лет) | +224% |
| Рост занятости в отрасли | +122% |
| Рост ВВП | 5–6% в год |
| Туристический поток | 1.5 млн / год |
| Оборот общепита (2022) | $826 млн (+86% за 4 года) |

**Драйверы роста:**
- Законодательные требования к POS-терминалам и фискализации (ЦОТУ)
- Обязательная безналичная оплата (Click, Payme, Uzum)
- Активная урбанизация — Ташкент как гастрономический хаб региона
- Международные сети входят на рынок (KFC, Dodo Pizza)
- Рост цифровизации HoReCa: +15–18% год к году

**Выводы для Marjon:**
- Рынок на ранней стадии активного роста — окно для входа открыто
- Подписочная модель ($10–50/мес) делает вход доступным для 90%+ заведений
- Фискализация обязательна — интеграция с ОФД УЗ = конкурентное преимущество
- Растущее число заведений = растущий TAM (Total Addressable Market)

### 1.2. Целевая аудитория

| Сегмент | Описание | Размер | Потребности |
|---------|----------|--------|------------|
| Кафе и чайхона | 5–20 столов, 3–10 сотрудников | ~60% рынка | Простота, низкая цена, склад, фискализация |
| Рестораны | 20–100 столов, 10–50 сотрудников | ~25% рынка | CRM, аналитика, лояльность, KDS |
| Фастфуд | Высокий поток, доставка | ~10% рынка | Скорость, KDS, интеграция с агрегаторами |
| Сети | 3+ точек | ~5% рынка | Мультифилиальность, HR, консолидированная аналитика |

### 1.3. Боли рынка — почему ресторану НУЖНА автоматизация

| # | Боль | Масштаб | Цена проблемы |
|---|------|---------|---------------|
| 1 | **Воровство и потери** | 5–15% выручки теряется на неконтролируемых списаниях, недобитых чеках | Кафе с оборотом $3 000/мес теряет $150–450/мес |
| 2 | **Бумажный учёт** | 60% малых заведений ведут учёт вручную (Excel, тетрадка). Погрешность 12–18% | 10–15 часов/неделю владелец тратит на подсчёты |
| 3 | **Иллюзия контроля** | Касса отдельно, склад отдельно, кухня отдельно — нет единой картины | Владелец не знает реальную прибыль |
| 4 | **Хаос на кухне** | Бумажные бегунки теряются, путаются, нечитаемы | Среднее время подачи +5–10 мин, жалобы гостей |
| 5 | **Нет аналитики** | Не знает топ-блюда, food cost, загрузку по часам | Принимает решения «на ощупь» |
| 6 | **Фискальный закон** | POS-терминалы и чеки обязательны. Штрафы за нарушения | Штраф или закрытие заведения |
| 7 | **Нестабильный интернет** | В регионах УЗ Wi-Fi пропадает. Если система облачная — работа встаёт | Потеря заказов, недовольство гостей |

**Почему 60% малых заведений до сих пор НЕ автоматизированы:**

| Барьер | Как Marjon решает |
|--------|------------------|
| **Дорого** (iiko от $12/мес + оборудование $500+) | Старт от ~$8/мес, работает на обычном телефоне/ПК |
| **Сложно** (R-Keeper внедрение — недели) | Онбординг 15 минут, демо без настройки |
| **Страх персонала** (саботаж «тотального контроля») | Фокус на помощь повару (техкарты, таймеры), не на слежку |
| **Не понимают зачем** | Показать цифры: «вы теряете 5–15% выручки» |
| **Нет ИТ-навыков** | Интерфейс как в телефоне, видео-обучение |

### 2.2. Детальный анализ ключевых конкурентов

#### ZimZim (zim-zim.uz)

**Сильные стороны:**
- Локальная разработка, знание рынка УЗ
- 500+ заведений — валидация product-market fit
- Простота: «никаких дорогих технологий — достаточно телефона и компьютера»
- 4 отдельных приложения (владелец/официант/повар/менеджер)
- QR-меню для гостей

**Слабые стороны:**
- Тарифы не публичные (непрозрачно)
- Нет CRM и системы лояльности
- Десктоп-версия для менеджера, НЕ для кухни
- Ограниченный функционал складского учёта
- Низкое количество установок в Google Play (~5 000)

**Что взять:**
- Подход «мобильный-первый» для работы в зале
- Отдельные роли для каждого приложения
- QR-меню для самообслуживания

#### Paloma365

**Сильные стороны:**
- 20 000+ клиентов по СНГ — проверенная система
- Самая низкая цена среди аналогов (от 134 700 UZS/мес)
- 10 лет на рынке — стабильность
- Модуль KDS (экран повара)
- Киоск самообслуживания
- Множество обучающих видео

**Слабые стороны:**
- Не узбекская компания — разрыв с локальным рынком
- Мало отзывов в App Store / Google Play
- Нет полноценной программы лояльности
- Нет QR-меню

**Что взять:**
- Модульная архитектура (каждая функция — отдельный модуль)
- Видео-обучение как часть онбординга
- Прозрачная ценовая политика

#### iiko

**Сильные стороны:**
- Мировой лидер — 50 000+ заведений
- Полный цикл: POS → CRM → Лояльность → Аналитика → KDS → Доставка
- ИИ для прогноза продаж и автозаказов поставщикам
- Интеграция с Uzum Tezkor и Yandex Eats в Узбекистане
- Платежи Click, Payme, Uzum Bank

**Слабые стороны:**
- Высокая цена (от $12–80/мес) — дорого для чайхоны
- Сложность внедрения и настройки
- Тяжёлый для малого бизнеса
- Зависимость от провайдера (Soft24.uz)

**Что взять:**
- ИИ-прогнозы — реализовать в будущих версиях
- Интеграция с агрегаторами доставки
- Геймификация в программе лояльности

#### R-Keeper / BUSOFT (Узбекистан)

**Сильные стороны:**
- 16 лет на рынке УЗ — максимальное доверие
- 1 000+ заведений в Узбекистане
- 21 модуль — покрывает всё
- Полная фискальная интеграция с налоговой УЗ
- KDS Pro для Windows — нативное решение

**Слабые стороны:**
- Минимальная цена $45/мес — дорого для стартапа
- Тяжёлый интерфейс (наследие Windows-эпохи)
- Длительное внедрение (недели → месяцы)

**Что взять:**
- Глубина фискальной интеграции
- Windows KDS как формат для кухни
- Модульная ценовая политика (21 модуль = платишь за нужное)

## 3. Позиционирование и конкурентный ров

### 3.1. Миссия

> Сделать автоматизацию ресторана в Узбекистане доступной для каждого заведения — от чайхоны на 5 столов до сети на 50 точек.

### 3.2. Позиция на рынке

```
                    Цена
                    ▲
         Дорого     │
                    │  iiko    R-Keeper
                    │
                    │         AliPOS
                    │
                    │  Paloma365
         Дёшево     │  ● MARJON    ZimZim
                    │
                    └──────────────────────► Функциональность
                  Базовая              Полная
```

**Marjon = Максимум функций по минимальной цене.**

Marjon занимает нишу «всё включено по доступной цене» — конкурируя с Paloma365 по цене, но предлагая полноту функций уровня iiko.

### 3.3. Слоган

> **Marjon — вся автоматизация ресторана в одном приложении.**

### 3.4. Конкурентный ров (Moat) — чем защищаемся от копирования

| Ров | Описание | Сила |
|-----|----------|------|
| **Switching cost** | После настройки меню, склада, персонала — переезд дорогой | Высокий |
| **Цена** | Самый дешёвый вход = сложно конкурировать тем, у кого legacy-расходы | Высокий |
| **Локальность** | Знание рынка УЗ, UZ-язык, локальные платежи, фискализация | Высокий |
| **Скорость итерации** | Маленькая команда = еженедельные релизы vs ежеквартально у iiko | Средний |
| **Сетевой эффект** | Чем больше заведений → лучше аналитика/прогнозы | Средний (в будущем) |

### 3.5. Долгосрочная стратегия

**Год 1: Grab the market** — максимально дешёвый вход, фокус на фастфуд и кафе, цель: 200 клиентов  
**Год 2: Lock them in** — программа лояльности, доставка (Uzum Tezkor), цель: 1000 клиентов  
**Год 3: Expand** — Казахстан, Кыргызстан, BI-аналитика, маркетплейс для поставщиков, цель: 3000+

## 4. Бизнес-модель

### 4.1. Модель монетизации

**SaaS-подписка** с ежемесячной оплатой. Без лицензий, без установки, без скрытых платежей.

| Тариф | Цена (UZS/мес) | ~USD | Целевой сегмент | Лимиты |
|-------|----------------|------|-----------------|--------|
| **Starter** | 100 000 | ~$8 | Чайхона, кофейня, 1 точка | 1 точка, 5 сотрудников, базовая аналитика |
| **Business** | 250 000 | ~$20 | Кафе, ресторан | 1 точка, 20 сотрудников, CRM, лояльность, доставка |
| **Pro** | 500 000 | ~$40 | Сеть, крупный ресторан | До 5 точек, безлимит сотрудников, BI-аналитика |
| **Enterprise** | Индивидуально | — | Крупные сети | Безлимит точек, выделенный менеджер, API |

### 4.2. Дополнительные доходы

| Источник | Описание | Примерная цена |
|----------|----------|----------------|
| SMS-уведомления | Пакеты SMS для лояльности и маркетинга | от 50 UZS/SMS |
| Доп. точки | Каждая дополнительная точка сверх тарифа | +50 000 UZS/мес |
| Внедрение | Помощь в настройке, обучение персонала | 500 000 – 2 000 000 UZS |
| Интеграции | Подключение к Uzum Tezkor, Yandex Eats | Индивидуально |
| White-label | Мобильное приложение под брендом заведения | Индивидуально |

### 4.3. Unit-экономика (прогноз на 12 месяцев)

| Метрика | Значение |
|---------|----------|
| Средний чек подписки | 250 000 UZS/мес (~$20) |
| Целевое кол-во клиентов (12 мес) | 200 |
| MRR (Monthly Recurring Revenue) | 50 000 000 UZS (~$4 000) |
| ARR (Annual Recurring Revenue) | 600 000 000 UZS (~$48 000) |
| Churn rate (целевой) | ≤5% |
| CAC (Customer Acquisition Cost) | ~500 000 UZS (~$40) |
| LTV (Lifetime Value) | ~6 000 000 UZS ($480) при retention 24 мес |
| LTV/CAC | 12x |

### 4.4. Go-to-Market стратегия

1. **Free trial** — 15 дней полного доступа, без привязки карты
2. **Freemium** — бесплатный доступ к демо-панели (работает сейчас через demo fallback)
3. **Direct sales** — прямые продажи в Ташкенте, посещение заведений
4. **Партнёрская программа** — комиссия 10% за каждого приведённого клиента
5. **Контент-маркетинг** — блог, видео-обучение, Telegram-канал

## 5. Общее описание платформы

### 5.1. Платформы

| Платформа | Назначение | Пользователь | Технология | Статус |
|-----------|-----------|--------------|------------|--------|
| **Web Admin** | Полное управление заведением | Владелец, Менеджер, Кассир | React SPA (Vite) | ✅ MVP (80%) |
| **Mobile App** | Работа в зале, удалённый контроль | Официант, Владелец | React Native / Expo | ❌ Не начато |
| **Desktop KDS** | Кухонный дисплей для поваров | Повар, Шеф-повар | Electron (EXE) | ❌ Не начато |
| **Print Agent** | Печать чеков и кухонных тикетов | POS-терминал | Python (polling) | ⚙️ Backend готов |

### 5.2. Единый бэкенд

Все платформы работают через **единый REST API** (FastAPI). Это означает:
- Одна база данных для всех платформ
- Одна авторизация (JWT + refresh tokens)
- Единый источник истины для данных
- Реальное время через WebSocket (кухня ↔ зал)

## 7. Offline-архитектура (Offline-First)

### 7.1. Почему это критично для Узбекистана

| Проблема | Частота | Последствия без офлайна |
|---------|---------|----------------------|
| Wi-Fi пропал в ресторане | 2–5 раз/день в регионах | Заказы не принимаются, кухня стоит |
| Мобильный интернет нестабилен | Постоянно за пределами Ташкента | Официант не может отправить заказ |
| Электричество отключили | 1–3 раза/месяц в регионах | ПК перезагружается, данные теряются |
| Сервер Marjon упал | Раз в месяц (реалистично для стартапа) | ВСЕ заведения не работают |

**Без офлайн-режима Marjon НЕПРИГОДЕН для 70% Узбекистана (за пределами Ташкента).**

### 7.2. Единая архитектура

```
┌────────────────────────────────────────────────┐
│            КЛИЕНТСКОЕ УСТРОЙСТВО               │
│                                                │
│  ┌──────────┐    ┌───────────────────────────┐ │
│  │ UI(React)│───▶│ Локальный Store            │ │
│  │          │◀───│ (IndexedDB / SQLite)       │ │
│  └──────────┘    │                           │ │
│                  │  Очередь синхронизации:    │ │
│                  │  order_create  [pending]   │ │
│                  │  order_status  [pending]   │ │
│                  │  item_ready    [synced]    │ │
│                  └──────────┬────────────────┘ │
│                             │                  │
│  ┌──────────────────────────▼────────────────┐ │
│  │     Sync Engine (фоновый процесс)        │ │
│  │  1. Ping API каждые 10 сек               │ │
│  │  2. Онлайн → отправить pending            │ │
│  │  3. Получить новые данные с сервера       │ │
│  │  4. Разрешить конфликты (server-wins)     │ │
│  └──────────────────────────┬────────────────┘ │
└─────────────────────────────┼─────────────────┘
                              │
                     ┌────────▼─────────┐
                     │  REST API / WS   │
                     │  (FastAPI)       │
                     └────────┬─────────┘
                     ┌────────▼─────────┐
                     │  PostgreSQL      │
                     └──────────────────┘
```

### 7.3. Что кэшируется локально

| Данные | Хранилище | Размер |
|--------|-----------|--------|
| Меню (блюда, категории, фото) | SQLite/IndexedDB | ~2–5 MB |
| Техкарты (рецепты, ингредиенты) | SQLite/IndexedDB | ~1 MB |
| Стоп-лист | SQLite/IndexedDB | ~1 KB |
| Активные заказы | SQLite/IndexedDB | ~50 KB |
| Столы и карта зала | SQLite/IndexedDB | ~10 KB |
| Настройки | JSON-файл / AsyncStorage | ~1 KB |
| Очередь действий (pending sync) | SQLite/IndexedDB | ~10 KB |

### 7.4. Поведение по платформам

**Официант (Mobile) — офлайн:** видит меню из кэша → создаёт заказ локально → при восстановлении связи Sync Engine отправляет pending → сервер принимает → KDS получает заказ. Пока офлайн — отнести заказ устно.

**Повар (Desktop KDS) — офлайн:** уже загруженные заказы ОСТАЮТСЯ на экране → повар продолжает → нажимает «Готово» → статус локально → при восстановлении — синхронизация. Новые заказы НЕ приходят.

**Web Admin — офлайн:** показать баннер «Нет подключения к серверу» → данные на экране остаются (не обновляются) → формы блокируются → при восстановлении — автоматический refresh.

### 7.5. Индикация состояния связи

| Статус | Цвет полосы | Текст |
|--------|------------|-------|
| Онлайн | Нет полосы | — |
| Синхронизация | Голубая | «Синхронизация...» + spinner |
| Офлайн | Оранжевая | «Нет соединения. Работа в офлайн-режиме» |
| Ошибка сервера | Красная | «Сервер недоступен» |
| Восстановлено | Зелёная (3 сек) | «Подключение восстановлено» |

### 7.6. Разрешение конфликтов — стратегия Server Wins

| Конфликт | Решение |
|---------|---------|
| Заказ создан офлайн, стол уже занят | Допустить 2 заказа на 1 стол |
| Блюдо «готово» офлайн, заказ отменён на сервере | Принять отмену, показать уведомление повару |
| Стоп-лист изменился пока был офлайн | Обновить при синхронизации, показать вспышку |

## 10. User Stories (для разработчиков)

### 10.1. Официант

- **US-W1:** Как официант, я хочу видеть карту столов с их статусами, чтобы быстро понять какие столы свободны.
- **US-W2:** Как официант, я хочу создать заказ одним пальцем за 30 секунд, чтобы не заставлять гостя ждать.
- **US-W3:** Как официант, я хочу получить push-уведомление когда блюдо готово, чтобы сразу забрать его с кухни.
- **US-W4:** Как официант, я хочу работать без интернета, чтобы не останавливаться если Wi-Fi упал.

### 10.2. Повар

- **US-C1:** Как повар, я хочу видеть новые заказы за 1 секунду после их создания, чтобы начать готовить без задержки.
- **US-C2:** Как повар, я хочу нажать одну кнопку чтобы отметить блюдо готовым, чтобы не отвлекаться от готовки.
- **US-C3:** Как повар, я хочу видеть техкарту (рецепт) по нажатию на блюдо, чтобы приготовить его правильно.
- **US-C4:** Как повар, я хочу чтобы просроченные заказы (>10 мин) мигали красным, чтобы я видел приоритеты.
- **US-C5:** Как повар, я хочу чтобы приложение работало когда Wi-Fi пропал, чтобы кухня не останавливалась.

### 10.3. Владелец

- **US-O1:** Как владелец, я хочу видеть выручку за сегодня в одной цифре, чтобы понять как идёт бизнес без открытия Excel.
- **US-O2:** Как владелец, я хочу получить push если кассир отменил заказ, чтобы контролировать злоупотребления.

### 12.2. Безопасность

> **⚠️ КРИТИЧЕСКИЙ РАЗДЕЛ — безопасность = доверие клиентов. Утечка данных = смерть стартапа.**

#### 12.2.1. Threat Model (модель угроз)

| Угроза | Вектор атаки | Последствия | Вероятность |
|--------|-------------|-------------|------------|
| **SQL Injection** | Ввод SQL в поля форм, URL параметры | Доступ ко всей БД, утечка данных всех клиентов | Высокая |
| **XSS (Cross-Site Scripting)** | Инъекция JS через комментарии к заказам, названия блюд | Кража JWT токенов, перехват сессий | Высокая |
| **CSRF (Cross-Site Request Forgery)** | Подделка запросов от имени авторизованного пользователя | Несанкционированные операции (отмена заказов, вывод денег) | Средняя |
| **Broken Authentication** | Перебор паролей, утечка JWT, отсутствие rate limiting | Доступ к чужому аккаунту | Высокая |
| **IDOR (Insecure Direct Object Reference)** | Подмена `order_id`, `company_id` в запросах | Просмотр/изменение чужих данных | Высокая |
| **Man-in-the-Middle** | Перехват трафика в незащищённой сети ресторана | Кража токенов, подмена данных | Средняя |
| **Злонамеренный сотрудник** | Кассир изменяет данные, менеджер удаляет записи | Финансовые потери владельца | Высокая |
| **DDoS** | Флуд запросами на API | Сервис недоступен для всех клиентов | Низкая |

| Сценарий | Параметры | Целевые показатели |
|---------|-----------|-------------------|

#### 12.6.5. CI/CD и автоматизация тестов

```
git push → GitHub Actions
     │

     ├── Unit тесты (Vitest + Pytest) — параллельно
     ├── Integration тесты (Pytest + test DB)
     │
     ├── [PR в main] → E2E тесты (Playwright)
     ├── [PR в main] → Security scan (Snyk / npm audit)
     │

     ├── [staging] → Smoke тесты (5 критических TC)
     │
     └── [manual] → Deploy to production
```

| Этап | Блокирует merge? | Время |

## 13. Онбординг и миграция

### 13.1. Путь нового клиента

**День 0:** Владелец узнаёт о Marjon → заходит на сайт → получает доступ к демо-панели (без регистрации!) → видит заполненные данные, играет с интерфейсом.

**День 1–3:** Создаёт аккаунт (телефон + SMS-код). Мастер настройки за 15 минут:
1. Название заведения, адрес, логотип
2. Добавить столы (карта зала — drag&drop)
3. Загрузить меню (вручную или из Excel-шаблона)
4. Добавить сотрудников (телефон + роль)
5. Настроить принтер (IP, тест-печать)

**День 4–15:** Активное использование → первые отчёты → понимает ценность → уведомление «Пробный период заканчивается через 3 дня».

**День 15+:** Выбирает тариф → оплата Click/Payme/Uzum/наличные → продолжает без перерыва.

### 13.2. Миграция с конкурентов

| Откуда | Что импортируем | Как |
|--------|----------------|-----|
| R-Keeper | Меню, категории, клиенты, поставщики | CSV-экспорт → импорт в Marjon |
| iiko | Меню, рецепты, склад, клиенты | CSV/Excel → парсер → импорт |
| Paloma365 | Меню, сотрудники | CSV → импорт |
| Excel/бумага | Меню | Excel-шаблон Marjon + ручной ввод |

**План миграции:** Неделя 1 (параллельная работа) → Неделя 2 (переключение) → Неделя 3+ (полный переход, старая система отключена).
