## 1. Боль рынка — почему ресторану НУЖНА автоматизация

### 1.1. Главные боли владельца (Jobs-to-be-Done)

| # | Боль | Масштаб | Цена проблемы |
|---|------|---------|---------------|
| 1 | **Воровство и потери** | 5–15% выручки теряется на неконтролируемых списаниях, недобитых чеках, «случайных» возвратах | Кафе с оборотом $3 000/мес теряет $150–450/мес |
| 2 | **Бумажный учёт** | 60% малых заведений ведут учёт вручную (Excel, тетрадка). Погрешность 12–18% | 10–15 часов/неделю владелец тратит на подсчёты |
| 3 | **Иллюзия контроля** | Касса отдельно, склад отдельно, кухня отдельно — нет единой картины | Владелец не знает реальную прибыль |
| 4 | **Хаос на кухне** | Бумажные бегунки теряются, путаются, нечитаемы. Повар не видит приоритет | Среднее время подачи +5–10 мин, жалобы гостей |
| 5 | **Нет аналитики** | Не знает топ-блюда, food cost, загрузку по часам, эффективность персонала | Принимает решения «на ощупь», а не на данных |
| 6 | **Фискальный закон** | В Узбекистане POS-терминалы и чеки обязательны. Штрафы за нарушения | Штраф или закрытие заведения |
| 7 | **Нестабильный интернет** | В регионах УЗ Wi-Fi пропадает. Если система облачная — работа встаёт | Потеря заказов, недовольство гостей |

### 1.2. Почему 60% до сих пор НЕ автоматизированы?

| Барьер | Описание | Как Marjon решает |
|--------|----------|------------------|
| **Дорого** | iiko от $12/мес + оборудование ($500+), R-Keeper от $45/мес | Старт от ~$8/мес, работает на обычном телефоне/ПК |
| **Сложно** | R-Keeper внедрение — недели, iiko — обучение дня | Онбординг 15 минут, демо без настройки |
| **Страх персонала** | Повара саботируют «тотальный контроль» | Фокус на помощь повару (техкарты, таймеры), не на слежку |
| **Не понимают зачем** | «У меня маленькое кафе, и так всё работает» | Показать цифры: «вы теряете 5–15% выручки» |
| **Нет ИТ-навыков** | Владелец — повар, а не программист | Интерфейс как в телефоне, видео-обучение |

## 3. Офлайн-архитектура (Offline-First)

### 3.1. Почему это критично для Узбекистана

| Проблема | Частота | Последствия без офлайна |
|---------|---------|----------------------|
| Wi-Fi пропал в ресторане | 2–5 раз/день в регионах | Заказы не принимаются, кухня стоит |
| Мобильный интернет нестабилен | Постоянно за пределами Ташкента | Официант не может отправить заказ |
| Электричество отключили | 1–3 раза/месяц в регионах | ПК перезагружается, данные теряются |
| Сервер Marjon упал | Раз в месяц (реалистично для стартапа) | ВСЕ заведения не работают |

**Вывод:** Без офлайн-режима Marjon НЕПРИГОДЕН для 70% Узбекистана (за пределами Ташкента).

### 3.2. Единая архитектура Offline-First

```
┌──────────────────────────────────────────────────────┐
│                  КЛИЕНТСКОЕ УСТРОЙСТВО                │
│                                                      │
│  ┌──────────────┐    ┌────────────────────────────┐  │
│  │  UI (React)  │───▶│  Локальный Store            │  │
│  │              │◀───│  (IndexedDB / SQLite)       │  │
│  └──────────────┘    │                            │  │
│                      │  Очередь синхронизации:    │  │
│                      │  ┌─────────────────────┐   │  │
│                      │  │ order_create  [pending]│  │
│                      │  │ order_status  [pending]│  │
│                      │  │ item_ready    [synced] │  │
│                      │  └─────────────────────┘   │  │
│                      └───────────┬────────────────┘  │
│                                  │                    │
│  ┌───────────────────────────────▼──────────────────┐│
│  │           Sync Engine (фоновый процесс)          ││
│  │                                                   ││
│  │  1. Проверить связь (ping API каждые 10 сек)     ││
│  │  2. Если онлайн → отправить pending из очереди   ││
│  │  3. Получить новые данные с сервера              ││
│  │  4. Разрешить конфликты (server-wins)            ││
│  │  5. Обновить локальный Store                     ││
│  └───────────────────────────────┬──────────────────┘│
└──────────────────────────────────┼───────────────────┘
                                   │
                          ┌────────▼─────────┐

                          │  (FastAPI)       │
                          └────────┬─────────┘
                                   │
                          ┌────────▼─────────┐
                          │  PostgreSQL      │
                          └──────────────────┘
```

### 3.3. Что кэшируется локально

| Данные | Хранилище | Обновление | Размер |
|--------|-----------|-----------|--------|
| Меню (блюда, категории, фото) | SQLite/IndexedDB | При старте + каждые 30 мин | ~2–5 MB |
| Техкарты (рецепты, ингредиенты) | SQLite/IndexedDB | При старте | ~1 MB |
| Стоп-лист | SQLite/IndexedDB | Push через WebSocket | ~1 KB |
| Активные заказы | SQLite/IndexedDB | Real-time (WS) + polling 10 сек | ~50 KB |
| Столы и карта зала | SQLite/IndexedDB | При старте | ~10 KB |
| Настройки (принтер, станция) | JSON-файл / AsyncStorage | При изменении | ~1 KB |
| Очередь действий (pending sync) | SQLite/IndexedDB | При каждом действии | ~10 KB |

### 3.4. Сценарии офлайн-работы

#### Официант (Mobile App) — офлайн

```
1. Официант подходит к столу, интернета нет
2. Открывает приложение → видит индикатор «ОФЛАЙН» (оранжевая полоса)
3. Видит меню из локального кэша (загружено утром)
4. Создаёт заказ → заказ сохраняется в SQLite со статусом pending_sync
5. На кухонном экране (Desktop KDS) заказ НЕ появляется (нет связи)
6. ⚠️ Официант должен отнести заказ на кухню устно или на бумаге
7. Интернет восстановился:
   → Sync Engine отправляет pending заказ на сервер
   → Сервер принимает, присваивает серверный ID
   → KDS получает заказ через WebSocket
   → Если повар уже готовит — статус обновляется
```

#### Повар (Desktop KDS) — офлайн

```
1. Wi-Fi пропал на кухне
2. Экран показывает «ОФЛАЙН» (красная полоса сверху)
3. Все уже загруженные заказы ОСТАЮТСЯ на экране
4. Повар продолжает работать с ними
5. Нажимает «Готово» → статус сохраняется локально (pending_sync)
6. Новые заказы НЕ приходят (нет WebSocket)
7. Интернет восстановился:
   → Все pending статусы отправляются
   → Пропущенные заказы загружаются
   → UI обновляется
```

#### Web Admin — офлайн

```
Web-панель работает ТОЛЬКО онлайн (это SPA в браузере).
При потере связи:
1. Показать баннер «Нет подключения к серверу»
2. Данные на экране остаются (но не обновляются)
3. Формы → «Сохранить» блокируется → показать сообщение
4. При восстановлении → автоматический refresh данных
```

### 3.5. Разрешение конфликтов

**Стратегия: Server Wins (с уведомлением)**

| Конфликт | Решение |
|---------|---------|
| Заказ создан офлайн, но стол уже занят другим заказом | Создать заказ на тот же стол (2 заказа на 1 стол допустимо) |
| Блюдо отмечено «готово» офлайн, но заказ отменён на сервере | Принять отмену, показать уведомление повару |
| Стоп-лист изменился пока был офлайн | При синхронизации обновить стоп-лист, показать вспышку |
| Два официанта создали заказ на один стол офлайн | Оба заказа сохраняются, менеджер объединит вручную |

### 3.6. Индикация состояния связи

| Статус | Цвет полосы | Текст | Где |
|--------|------------|-------|-----|
| Онлайн | Нет полосы (скрыта) | — | Все платформы |
| Синхронизация | Голубая | «Синхронизация...» + spinner | Все платформы |
| Офлайн | Оранжевая | «Нет соединения. Работа в офлайн-режиме» | Mobile, Desktop |
| Ошибка сервера | Красная | «Сервер недоступен» | Все платформы |
| Восстановлено | Зелёная (3 сек) | «Подключение восстановлено» | Все платформы |

## 4. Онбординг: как новый клиент начинает

### 4.1. Путь клиента (Customer Journey)

```
День 0: Знакомство
  → Владелец узнаёт о Marjon (реклама, сарафан, визит менеджера)
  → Заходит на сайт / звонит
  → Получает доступ к демо-панели (без регистрации!)
  → Видит заполненные данные, играет с интерфейсом

День 1–3: Пробный период (15 дней бесплатно)
  → Создаёт аккаунт (телефон + SMS-код)
  → Мастер настройки (5 шагов, 15 минут):
     1. Название заведения, адрес, логотип
     2. Добавить столы (карта зала — drag&drop)
     3. Загрузить меню (вручную или из Excel-шаблона)
     4. Добавить сотрудников (телефон + роль)
     5. Настроить принтер (IP, тест-печать)
  → Может начать работать СРАЗУ

День 4–15: Активное использование
  → Владелец видит первые отчёты
  → Понимает, какие блюда продаются, какие — нет
  → Видит реальную выручку vs «на глазок»
  → Получает уведомление: «Ваш пробный период заканчивается через 3 дня»

День 15+: Подписка
  → Выбирает тариф (Starter / Business / Pro)
  → Оплата: Click / Payme / Uzum / Наличные через партнёра
  → Продолжает работать без перерыва
```

### 4.2. Мастер настройки (Setup Wizard)

**Шаг 1: Заведение**
- Название
- Тип (ресторан / кафе / фастфуд / чайхона / бар)
- Адрес
- Логотип (загрузка файла или камера)
- Режим работы

**Шаг 2: Зал и столы**
- Выбрать layout (простая сетка или свободное размещение)
- Добавить столы (drag&drop)
- Указать количество мест на каждом столе

**Шаг 3: Меню**
- Добавить категории (шаблоны: Первые блюда, Вторые, Салаты, Напитки...)
- Добавить блюда (название, цена, описание, фото)
- Или: загрузить из Excel/CSV (шаблон скачивается)

**Шаг 4: Персонал**
- Добавить кассира (телефон → SMS-приглашение)
- Добавить официантов
- Добавить поваров

**Шаг 5: Оборудование**
- Подключить принтер (IP/порт, тест-печать)
- Подключить KDS (ссылка на скачивание EXE)
- Пропустить (всё можно подключить позже)

## 5. Миграция с конкурентов

### 5.1. Импорт данных

| Откуда | Что импортируем | Как |
|--------|----------------|-----|
| R-Keeper | Меню, категории, клиенты, поставщики | CSV-экспорт из R-Keeper → импорт в Marjon |
| iiko | Меню, рецепты, склад, клиенты | CSV/Excel → парсер → импорт |
| Paloma365 | Меню, сотрудники | CSV → импорт |
| Excel/бумага | Меню | Excel-шаблон Marjon + ручной ввод |
| Нет ничего | Всё с нуля | Мастер настройки + ручной ввод |

### 5.2. План миграции для заведения

```
Неделя 1: Параллельная работа
  → Marjon работает рядом со старой системой
  → Персонал учится на Marjon, но заказы всё ещё в старой
  
Неделя 2: Переключение
  → Все заказы через Marjon
  → Старая система — только как backup
  
Неделя 3+: Полный переход
  → Старая система отключена
  → Все данные в Marjon
```

## 6. Risk Matrix — риски проекта

### 6.1. Технические риски

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| Сервер Marjon упал | Средняя | Критическое | Офлайн-режим + несколько серверов (Supabase = managed) |
| Потеря данных | Низкая | Критическое | Ежедневные бэкапы Supabase + WAL |
| WebSocket нестабилен | Высокая | Среднее | Fallback на polling каждые 10 сек |
| Electron EXE тяжёлый | Средняя | Низкое | Оптимизация: Electron Forge, custom build |
| React Native баги на Android | Высокая | Среднее | Тестирование на 5+ устройствах |

### 6.2. Бизнес-риски

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| AliPOS скопирует функции | Высокая | Среднее | Быстрее итерировать, лучше UX, ниже цена |
| iiko/R-Keeper снизят цены | Низкая | Высокое | Фокус на простоту (они не смогут упростить legacy) |
| Не наберём 100 клиентов за 6 мес | Средняя | Критическое | Direct sales в Ташкенте + партнёрская сеть |
| Команда разработки — 1–2 чел | Высокая | Высокое | Максимальное переиспользование кода (web → mobile → desktop) |
| Закон изменится (фискализация) | Низкая | Среднее | Модульная архитектура, быстрая адаптация |

### 6.3. Рыночные риски

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| Рынок УЗ слишком маленький | Низкая | Высокое | Plan B: Казахстан, Кыргызстан (Paloma365 уже вышла в 10+ стран) |
| Ресторан не хочет платить | Средняя | Среднее | Freemium + ROI-калькулятор: «вы теряете X тыс./мес без нас» |
| Экономический кризис | Низкая | Высокое | Фокус на снижение потерь (= экономия для клиента) |

## 7. Конкурентный ров (Moat)

### 7.1. Чем Marjon защищается от копирования?

| Ров | Описание | Сила |
|-----|----------|------|
| **Сетевой эффект** | Чем больше заведений → тем больше данных → лучше аналитика/прогнозы | Средний (в будущем) |
| **Switching cost** | После настройки меню, склада, персонала — переезд дорогой | Высокий |
| **Скорость итерации** | Маленькая команда = быстрые релизы (еженедельно vs ежеквартально у iiko) | Средний |
| **Цена** | Самый дешёвый вход = сложно конкурировать тем, у кого legacy-расходы | Высокий |
| **Локальность** | Знание рынка УЗ, UZ-язык, локальные платежи, фискализация | Высокий |
| **Данные** | Агрегированные данные по индустрии (средний чек, food cost по категориям) | Слабый (пока) |

### 7.2. Долгосрочная стратегия

```
Год 1: Grab the market
  → Максимально дешёвый вход
  → Фокус: фастфуд и кафе (быстрый PMF, как AliPOS и Paloma365)
  → Цель: 200 клиентов

Год 2: Lock them in
  → Программа лояльности (клиенты заведения привязаны к Marjon)
  → Доставка (интеграция с Uzum Tezkor)
  → Цель: 1000 клиентов

Год 3: Expand
  → Казахстан, Кыргызстан
  → BI-аналитика, ИИ-прогнозы
  → Маркетплейс для поставщиков (поставщик → Marjon → все его рестораны)
  → Цель: 3000+ клиентов
```

## 8. User Stories (для разработчиков)

### 8.1. Официант

```
US-W1: Как официант, я хочу видеть карту столов с их статусами,
       чтобы быстро понять какие столы свободны.

US-W2: Как официант, я хочу создать заказ одним пальцем за 30 секунд,
       чтобы не заставлять гостя ждать.

US-W3: Как официант, я хочу получить push-уведомление когда блюдо готово,
       чтобы сразу забрать его с кухни.

US-W4: Как официант, я хочу работать без интернета,
       чтобы не останавливаться если Wi-Fi упал.
```

### 8.2. Повар

```
US-C1: Как повар, я хочу видеть новые заказы за 1 секунду после их создания,
       чтобы начать готовить без задержки.

US-C2: Как повар, я хочу нажать одну кнопку чтобы отметить блюдо готовым,
       чтобы не отвлекаться от готовки.

US-C3: Как повар, я хочу видеть техкарту (рецепт) по нажатию на блюдо,
       чтобы приготовить его правильно.

US-C4: Как повар, я хочу чтобы просроченные заказы (>10 мин) мигали красным,
       чтобы я видел приоритеты.

US-C5: Как повар, я хочу чтобы приложение работало когда Wi-Fi пропал,
       чтобы кухня не останавливалась.
```

### 8.3. Владелец

```
US-O1: Как владелец, я хочу видеть выручку за сегодня в одной цифре,
       чтобы понять как идёт бизнес без открытия Excel.

US-O2: Как владелец, я хочу получить push если кассир отменил заказ,
       чтобы контролировать злоупотребления.

US-O3: Как владелец, я хочу видеть себестоимость каждого блюда,
       чтобы знать на чём я зарабатываю, а на чём теряю.

US-O4: Как владелец, я хочу запустить систему за 15 минут,
       чтобы не тратить неделю на внедрение.

US-O5: Как владелец, я хочу платить от 100 000 UZS/мес,
       чтобы автоматизация не стоила дороже проблемы.
```

### 8.4. Менеджер

```
US-M1: Как менеджер, я хочу видеть Z-отчёт за текущую смену,
       чтобы закрыть кассу правильно.

US-M2: Как менеджер, я хочу добавить нового сотрудника за 1 минуту,
       чтобы он мог начать работать в тот же день.

US-M3: Как менеджер, я хочу видеть остатки на складе,
       чтобы заказать продукты до того как они закончатся.
```
