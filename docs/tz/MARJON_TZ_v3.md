# 1. Общие сведения

## 1.1. Что такое Marjon

Marjon — облачная операционная система для ресторана: один бэкенд и несколько клиентов (интерфейсов), которые закрывают полный цикл заведения — от брони стола и приёма заказа до кухни, раздачи, кассы, склада, финансов и отчётности владельца.

Ключевая идея: **одни данные — много экранов**. Заказ, созданный на кассе, сразу виден на кухне, после готовности — на экране раздачи, после подтверждения — на телевизоре в зале; оплата автоматически списывает продукты по тех-картам и попадает в финансовую отчётность.

## 1.2. Границы системы

В систему входят:

- **Веб-панель владельца** — управление заведением из браузера (дашборд, отчёты, меню, склад, финансы, сотрудники, настройки).
- **POS-десктоп** — рабочее место кассира/официанта/курьера (Windows, Electron).
- **Кухонный экран (KDS)** — браузерный экран для поваров.
- **Экран раздачи (Expo)** — браузерный экран подтверждения готовых заказов.
- **Гостевой ТВ-экран** — публичная страница с номерами заказов, без авторизации.
- **Мобильное приложение** — Flutter-клиент для Android/iOS с теми же режимами работы.
- **HQ-админка** — внутренняя панель платформы (организации, тарифы, склад платформы, финансы, справочники).
- **Сайт и магазин** — лендинг `marjon.tech` и страница дистрибутивов `/store`.
- **API** — единый REST/WebSocket интерфейс `/api/v1`, через который работают все клиенты.

## 1.3. Термины

| Термин | Значение |
| --- | --- |
| Компания (Company) | Одно заведение-арендатор (tenant). Свои сотрудники, меню, склад, финансы. |
| Филиал (Branch) | Точка продаж внутри компании. У филиала свои залы, столы, принтеры, экран очереди. |
| Моноблок | Терминал (касса), привязанный к филиалу. Вход на десктоп — по телефону и паролю сотрудника с ролью «Моноблок». |
| Заказ (Order) | Единица продажи: зал, с собой, доставка или QR. Содержит позиции, суммы, статус. |
| Позиция (OrderItem) | Блюдо в заказе с количеством, ценой, модификаторами, статусом приготовления. |
| Дозаказ | Добавление блюд в уже отправленный заказ. Кухня получает только новые позиции, счёт у кассира остаётся полным. |
| KDS | Kitchen Display System — кухонный экран. |
| Expo (раздача) | Экран, где подтверждают, что все блюда заказа готовы и его можно выдавать. |
| Гостевой экран | Телевизор в зале: очередь и готовые номера заказов. |
| Тех-карта | Рецепт блюда: состав из сырья с нормами расхода. Основа автосписания со склада. |
| Полуфабрикат (ПФ) | Заготовка с собственной тех-картой и выходом. |
| FIFO | Списание со склада по партиям: раньше пришло — раньше списалось. |
| Z-отчёт | Итоговый отчёт смены/периода по кассирам, официантам, местам, меню. |
| RBAC | Ролевая модель доступа: роли → разрешения (module:action). |

# 2. Роли и доступ

## 2.1. Роли компании

Канонические роли сотрудников (единый справочник в `backend/app/modules/rbac/constants.py`):

| Слаг | Роль | Основное рабочее место |
| --- | --- | --- |
| `owner` | Владелец | Веб-панель |
| `manager` | Менеджер | Веб-панель, POS |
| `cashier` | Кассир | POS-десктоп |
| `waiter` | Официант | POS-десктоп |
| `monoblock` | Моноблок (терминал) | POS-десктоп, KDS |
| `kitchen` | Повар | KDS |
| `courier` | Курьер | POS-десктоп (режим «Курьер») |
| `warehouse` | Завсклад | Веб-панель, склад |

Особенности:

- В **веб-панель** пускается только роль `owner` (проверка `isOwnerWebUser`: сессия приложения, есть компания, не супер-админ, ровно роль owner). Остальные роли работают через десктоп/KDS.
- Роль `admin` — историческая, сохранена в БД, но прав не даёт (закрыта осознанно).
- Супер-админ платформы — флаг `is_superadmin` + отдельная сессия `hq_admin`; в роли компании не входит.

## 2.2. Права (RBAC)

Разрешение = `модуль:действие` + область (`self`, `branch`, `company`). Полный каталог — 40 разрешений:

| Модуль | Разрешения |
| --- | --- |
| POS | `orders:create`, `orders:read`, `orders:update`, `orders:cancel` |
| Номенклатура | `products:create/read/update`, `categories:create/read` |
| Склад | `stock:read`, `stock:write` |
| Платежи | `process`, `read` |
| Кухня | `orders:read`, `items:update`, `stations:manage` |
| CRM | `customers:read/write` |
| HR | `employees:read/write`, `shifts:manage` |
| Аналитика | `dashboard`, `reports` |
| Доставка | `orders:manage`, `couriers:manage` |
| Уведомления | `send`, `read` |
| Аудит | `read` |
| Фискализация | `receipts:manage` |
| Подписки | `manage` |
| Принтеры | `manage`, `print` |
| RBAC | `roles:manage`, `users:manage` |
| Компания | `manage`, `branches:manage` |
| Финансы | `manage`, `read` |

Наборы по умолчанию закреплены за ролями: владелец — полный бизнес-набор, менеджер — почти всё операционное, кассир — заказы + оплаты + чтение финансов, официант — заказы без закрытия счёта, повар — только кухня, курьер — доставка, завсклад — номенклатура и склад.

## 2.3. Тумблеры сотрудника

Помимо ролей, у каждого сотрудника есть 16 персональных прав, которые владелец включает в карточке:

`can_delete_dishes`, `can_change_marking_code`, `can_takeaway_at_table`, `can_change_order_type`, `can_close_bill`, `can_open_cash_drawer_after_payment`, `can_view_closed_orders`, `can_manage_orders`, `can_main_monoblock`, `can_see_cashiers`, `can_cook_printer`, `can_print_cancel`, `can_kitchen`, `can_expo`, `can_view_finance`, `can_approve_attendance`.

Правила:

- Тумблер `can_kitchen` открывает моноблоку вход на кухонный экран.
- `can_expo` даёт доступ к экрану раздачи.
- На десктопе действует принцип «нет ключа — разрешено» для обратной совместимости, поэтому явный `false` сохраняется только если право реально выдавалось; это защищает легаси-сотрудников от случайного отзыва прав.

## 2.4. Вход, сессии, безопасность доступа

- **Веб-панель:** телефон + пароль → `POST /auth/login` → access-токен (15 минут) + refresh (30 дней). «Запомнить меня» управляет сохранением refresh.
- **POS-десктоп:** один раз указывается адрес сервера; затем вход моноблока телефоном и паролем → экран PIN сотрудника (4 цифры, автопроверка) → режим работы. Смена закрыта — вместо цифр предлагается открыть смену.
- **KDS:** привязка устройства (моноблок с включённым правом «Кухня» или вход по логину филиала) → выбор повара из списка → PIN.
- **Раздача:** обычный вход сотрудника телефоном/паролем; доступ по праву «Раздача».
- **ТВ:** без авторизации, только чтение публичного экрана филиала.
- **HQ:** отдельный эндпоинт `/auth/admin/login`, отдельные ключи токенов, проверка «супер-админ + scope hq_admin».
- Токен несёт область (`app`, `hq_admin`, `kitchen`) и версию авторизации; смена пароля инвалидирует старые сессии.
- Кухонная сессия ограничена белым списком путей, филиал берётся из токена.
- Rate limiting: логин 5/мин, регистрация 5/мин, админ-логин 10/мин, refresh 30/мин.
- CORS — только явно разрешённые origin; wildcard отбрасывается.
- Аудит: журнал действий (кто, что, сущность, было/стало, IP, устройство), чтение — владелец.

## 3.2. Домены бэкенда

Бэкенд разделён на 32 модуля. Ключевые:

- `auth` — вход, токены, пользователи, PIN, кухонные сессии.
- `companies` — компания, филиалы, лого, настройки заказа.
- `rbac` — роли, разрешения, назначения.
- `pos` — заказы, позиции, смены, терминалы.
- `payments` — оплаты, провайдеры, вебхуки.
- `kitchen` — KDS, станции, раздача, гостевой экран, WebSocket.
- `inventory` — номенклатура, тех-карты, партии, склады, документы склада.
- `warehouse` — приход, перемещение, инвентаризация, списание, отходы, расход.
- `halls` — залы, столы, раскладка.
- `finance` — денежные операции, категории, контрагенты, кассы.
- `analytics` — дашборд, продажи, Z-отчёт.
- `admin_reports` — 7 отчётов владельца.
- `hr` — сотрудники, смены, посещаемость, история входов.
- `printers` — принтеры, задания печати, шаблоны чеков, WebSocket.
- `fiscal` — фискализация и outbox.
- `crm`, `loyalty`, `delivery`, `notifications`, `ratings`, `audit`.
- `subscriptions` — тарифы, подписки, счета.
- HQ-модули: `organizations`, `handbook`, `marketing`, `tasks`, `field_service`, `storage`, `admin_settings`, `departments`.

## 3.3. Мультитенантность

- Каждая запись бизнес-данных привязана к `company_id`, операционные — ещё и к `branch_id`.
- `TenantMiddleware` кладёт идентификаторы из токена в контекст запроса; фактическую изоляцию обеспечивают guard'ы зависимостей и фильтр по филиалу (`effective_branch_filter`).
- Сотрудник видит только свой филиал; владелец — всю компанию.

## 3.4. Реальное время

- WebSocket кухни: `/ws/kitchen?token=…&branch_id=…`, канал `kitchen:{company}:{branch}`. События: `new_order`, `order_updated`, `order_cancelled`, `item_status_changed`, `order_completed`.
- WebSocket печати: `/printers/ws/{branch_id}`, канал `printers:{company}:{branch}`. Клиент забирает задания и подтверждает выполнение.
- Клиенты дублируют сокет опросом (KDS — 5 с, раздача — 4 с, ТВ — 4 с), поэтому потеря сокета не останавливает работу.

## 3.5. Офлайн-поведение (как реализовано)

- Десктоп кэширует GET-ответы в localStorage и показывает последние данные при потере сети.
- Очередь записи (`marjon_write_queue`) хранит только смены статусов заказов/позиций и отправляется при восстановлении связи или раз в 15 секунд.
- **Оплата в офлайн-очередь не ставится** — деньги проводятся только при живом сервере. Это осознанное ограничение: нельзя рисковать двойным списанием.
- KDS и раздача при потере связи показывают индикатор и последние данные; изменения без сервера не сохраняются.
- Серверная сущность `OfflineJob` (идемпотентные задания) присутствует в БД, но фонового обработчика нет.

## 3.6. Мультиязычность

- Языки интерфейса: русский, узбекский, английский. Бандлы `ru.json` / `uz.json` / `en.json` (~3270 ключей на русском), `i18next` + `react-i18next`, выбор хранится в `marjon_lang`, fallback — русский.
- Функция `t()` принимает как ключ, так и русский текст (обратный индекс), поэтому подписи в конфигах модулей переводятся без дублирования.
- Лендинг имеет отдельные ru/uz версии.
- HQ-админка переключателя языка не имеет (русский интерфейс).
- В БД есть таблицы языков и переводов и API экспорта/импорта, но UI к ним не подключён.

# 4. Сквозные бизнес-процессы

## 4.1. Регистрация и онбординг

1. Владелец регистрируется (`POST /auth/register`): создаются компания, «Основной филиал», владелец, базовые единицы измерения.
2. В настройках заполняются профиль заведения (название, адрес, телефон, ИНН, логотип), часы начала дня, ставка НДС, язык.
3. Создаются залы и столы, принтеры, способы оплаты, сотрудники.
4. Заводится меню: категории → блюда/товары → тех-карты (расход сырья) → стоп-лист/лимиты.
5. Приходуется сырьё на склад.
6. Терминал подключается к серверу и входит моноблоком; кухня и раздача открываются по ссылкам.

## 4.2. Открытие смены

- Кассир на PIN-экране (если смена закрыта) или в разделе «Финансы» открывает смену; фиксируется начальная наличность.
- На кассира может быть только одна открытая смена.
- Пока смена не открыта, касса не проводит оплаты.

## 4.3. Приём заказа

1. Кассир/официант выбирает тип: **в зале**, **с собой**, **доставка** (набор ограничен настройкой компании).
2. Для зала выбирается свободный стол из зоны; для доставки указываются телефон и адрес.
3. Блюда добавляются кликом; в карточке блюда — количество/сумма, добавки (модификаторы), комментарий, отметка «с собой».
4. При сохранении заказ получает номер и уходит на кухню; печатается кухонный тикет (и чек — по настройке).
5. **Дозаказ:** новые блюда добавляются в тот же заказ. Кухня получает только новые позиции, кухонный тикет формируется по ним; у кассира счёт остаётся полным.
6. Заказ можно перенести на другой стол (с причиной), сменить официанта, отменить целиком или отдельную позицию (отмена требует пароля, если он задан в компании).
7. Пустой заказ автоматически отменяется.

**Статусы заказа:** `new → accepted → cooking → ready → completed` (в любую сторону до `completed` допускаются рабочие переходы), `cancelled` — терминальный. Позиции: `pending → cooking → ready → served`, `cancelled`.

## 4.4. Кухня и дозаказ

- Повар видит карточки заказов с таймером, составом, комментариями и пометками «с собой».
- Каждую позицию можно отметить «Сделал» (`ready`) или вернуть «Не сделал» (`cooking`).
- Кнопка «Весь стол готов» переводит заказ в `ready` и разрешена только когда все позиции готовы.
- При появлении нового заказа звучит сигнал; пороги подсветки — 10 и 20 минут (настраиваются на десктопе).
- Дозаказ приходит как обновление заказа; новые позиции добавляются в карточку.

## 4.5. Раздача и гостевой экран

1. Когда все позиции заказа готовы, заказ появляется на экране раздачи.
2. Сотрудник раздачи нажимает «Подтвердить — повар всё сделал».
3. Заказ получает отметку `expo_confirmed_at` и попадает на гостевой экран в колонку «готов».
4. На ТВ заказ показывается только после подтверждения раздачи; неподтверждённые в очередь гостя не попадают.

## 4.6. Оплата

- Способы: наличные, карта, Payme, Click, Uzum, баллы лояльности, в долг (контрагенту).
- Сумма оплаты должна совпадать с итогом заказа; переплата наличными допустима (сдача), карта — нет. Частичных оплат нет.
- Смешанная оплата «наличные + карта» поддерживается на уровне API, в интерфейсе десктопа выбирается один способ.
- После оплаты заказ становится `completed`, списываются продукты по тех-картам (FIFO), ставится фискальный чек в outbox, при необходимости открывается денежный ящик.
- Долг: создаётся контрагент-клиент с балансом; официанту долг запрещён.
- Возврат/переоткрытие: `completed → accepted` с причиной; предыдущие оплаты помечаются `refunded`, пересчитывается сдача.

## 4.7. Печать

- Типы принтеров: чековый, кухонный, барный, этикетки.
- Печать выполняет сервер: задание ставится в очередь, клиент получает его по WebSocket, печатает и подтверждает. При недоступности клиента сервер пробует прямой канал.
- Печатаются: клиентский чек, кухонный тикет, сводка, Z-отчёт, повтор чека, пакетная печать (сотрудники, тех-карты, приходы, инвентаризации).
- В кухонном тикете блок отмены содержит причину.
- Шаблон чека настраивается по блокам: шапка (лого, название, адрес, телефон), заказ (номер, стол, официант, дата), состав, итоги (скидка, сервисный сбор, НДС, сумма, способ оплаты), подвал (благодарность, нижний номер).

## 4.8. Закрытие смены и Z-отчёт

- Закрытие — в профиле сотрудника: вводится наличность на конец, смена закрывается. Закрытие блокируется, если у кассира есть свои незакрытые заказы.
- Z-отчёт формируется за период и печатается по разрезу: кассиры, официанты (с процентом обслуживания), места, меню. Z-отчёт — печатный документ; на экране отображаются только параметры и журнал печати. X-отчёта нет.

## 4.9. Складской цикл

1. **Приход** (накладная): поставщик, склад, дата, позиции. Сохранение сразу проводит документ и увеличивает остаток партиями.
2. **Продажа**: при оплате заказа сервер списывает ингредиенты по тех-картам со склада (FIFO), идемпотентно по паре «ингредиент + склад».
3. **Расход**: ручной документ с предпроверкой остатка; при нехватке автоматически создаётся отход.
4. **Перемещение**: документ между складами (в веб-интерфейсе доступен только просмотр).
5. **Инвентаризация**: вводятся фактические остатки; излишек проводится приходом, недостача — расходом.
6. **Списание**: документы причин списания не влияют на остатки (учёт потерь).
7. **Отход**: отдельный документ производства/порчи с авто- и ручными строками.
8. **Остатки**: дерево складов, категорий и сырья на дату; партии хранятся, но в интерфейсе не показываются.

## 4.10. Финансовый цикл

- Денежные операции: приход и расход с категорией, способом оплаты, контрагентом, комментарием.
- Справочники: категории приходов/расходов, способы оплаты, контрагенты (клиенты, поставщики, прочие).
- Касса: баланс, операции, движение денег, расходы по категориям, разбивка по способам оплаты.
- Дебиторка/кредиторка: долги клиентов и обязательства перед поставщиками, сальдо.
- Идемпотентность: финансовые операции защищены ключом идемпотентности.

## 4.11. Персонал

- Карточка сотрудника: фото, имя, телефон (логин), пароль, PIN, роль, филиал, принтер, статус, 16 тумблеров.
- Архив сотрудников: активные/архивированные.
- История входов: кто, роль, телефон, время, устройство/IP.
- Посещаемость: отметки прихода/ухода (PIN, QR, вручную), подтверждение/отклонение, журнал и отработанное время.
- Смены сотрудников: плановые/активные/завершённые/отсутствие; тип оплаты — фиксированная, почасовая, процент.

## 4.12. Справочники и настройки

Залы и столы (вместимость, процент обслуживания, тип ценообразования), единицы измерения (системные и свои), способы оплаты, принтеры, шаблоны чеков, филиалы с логином/паролем терминала, профиль компании, НДС, часы начала дня, экран очереди.

# 6. POS-десктоп

Платформа: Windows (Electron), установщик и portable. Экран оптимизирован под сенсорный терминал и клавиатуру.

## 6.1. Первый запуск и подключение

- Экран настройки сервера: адрес (по умолчанию `https://api.marjon.tech/api/v1`), кнопка «Проверить соединение» (GET `/health`, таймаут 5 с), сохранение нормализует адрес до `…/api/v1`.
- Далее — вход моноблока: телефон +998 и пароль, маска ввода, показ пароля, доступ к настройкам до входа.

## 6.2. Вход и режимы

1. PIN сотрудника: 4 цифры, проверка автоматически, поддержка физической клавиатуры, ошибка — вибрация и повтор.
2. Роль определяет режим: касса, официант, курьер. Повару касса запрещена — он работает на KDS.
3. Режимы используют один экран, различаются доступными разделами и правами.
4. Блокировка: через 15 минут бездействия; разблокировка своим PIN, чужой PIN переключает сотрудника.

## 6.3. Зал и столы

- Зоны (залы) и столы из настроек; навигация «Все» + зоны со счётчиком свободных.
- Статусы стола: свободен, занят, готов, ожидает (чек напечатан).
- Две доски: «Все столы» и «По официантам»; у официанта 12 ячеек с «Добавить заказ», карточки перетаскиваются, раскладка запоминается.
- Типы заказа: в зале, с собой, доставка; переключатель виден по праву и настройке компании.
- Режим «Курьер»: только доска доставки, без столов, всё «с собой».

## 6.4. Заказ и корзина

- Создание: `+` → выбор зала и свободного стола → меню.
- Блюдо добавляется кликом; карточка позиции: количество или сумма, добавки, комментарий, «с собой», удаление.
- После отправки позиция read-only: видно, кто и когда добавил; доступна отмена блюда (по праву).
- Дозаказ: «Добавить блюда» досылает новые позиции одним кухонным тикетом; «К оплате» переходит к расчёту.
- Перенос на другой стол — с причиной; смена официанта — в оплате.
- Отмена заказа — с причиной и паролем, если он задан.
- Скидка — процентом на этапе оплаты. Сервисный сбор рассчитывается автоматически (процент зала для зала, ставка компании иначе) и в ручную не редактируется.

## 6.5. Оплата

- Методы: наличные, карта, пользовательские способы из веб-настроек, «в долг» (если разрешено и это не переоткрытие).
- Одно поле суммы: пусто — ровно к оплате; больше — сдача; меньше — «Не хватает», закрытие блокируется. Карта не может переплатить.
- Долг: карточка с именем и телефоном должника; создаётся контрагент и долг.
- Возврат/переоткрытие: показывается «оплачено ранее / вернуть клиенту», долг запрещён.
- Каждая оплата защищена ключом идемпотентности; успех — только ответ `completed` с совпадающей суммой.
- После оплаты: заказ завершён, печатается чек, при праве открывается денежный ящик.

## 6.6. Печать

- Чековый принтер берётся из карточки сотрудника, иначе — первый принтер типа «чек».
- Печать серверная: задание → WebSocket → локальная печать → подтверждение; при офлайне клиента сервер пробует прямой канал.
- Повтор чека — из оплаты и из истории; пакетная печать — сводки сотрудников, тех-карт, приходов, инвентаризаций.

## 6.7. История, отчёты, стоп-лист, финансы

- **История** (`История`): фильтр по типу, «Печать сводки», «Вернуть в работу» для завершённых (по праву), пересчёт сдачи.
- **Отчёты:** «Блюда», «Сотрудники», «Z-отчёт» (только по праву), период, фильтр по имени, печать.
- **Стоп-лист:** сетка блюд, тумблер доступности, дневной лимит, история.
- **Финансы:** касса, операции (по праву), открытие смены.

## 6.8. Сотрудники, посещаемость, склад

- «Сотрудники» (по праву): список, карточка, создание/редактирование, PIN.
- «События» (посещаемость): очередь на подтверждение, отметка прихода/ухода, журнал за день, прошлые дни по праву.
- «Склад» (по праву): приход, ручное списание, инвентаризация. Автосписание по продажам выполняет сервер.

## 6.9. Настройки и офлайн

- Настройки: звук (громкость, проверка), таймеры кухни (жёлтый 5 мин / красный 10 мин), экран (полный экран, масштаб, автозапуск), **«Экран очереди»** (гостевой ТВ вкл/выкл для филиала), язык, тема, адрес сервера, диагностика принтеров.
- Офлайн: кэш GET-данных, очередь только для смен статусов, оплаты — нет. При восстановлении связи очередь отправляется.

# 7. Кухонный экран (KDS)

Адрес: `https://kitchen.marjon.tech`. Тёмная тема по умолчанию.

## 7.1. Вход

1. Привязка устройства:
   - вкладка «Моноблок» — телефон и пароль сотрудника с включённым правом «Кухня» (вызов `/auth/kitchen/monoblock-session`);
   - вкладка «Филиал» — логин и пароль филиала (вызов `/auth/kitchen/session`).
2. Если у моноблока несколько филиалов — выбор филиала.
3. Если кухня выключена в карточке моноблока — сообщение «Кухня выключена в карточке моноблока».
4. Выбор повара из списка (карточки; без PIN — «PIN не задан»).
5. PIN 4 цифры — вход на доску.

## 7.2. Доска

- Одна доска без разбивки по станциям; табы «Все / В работе / Готовые»; сортировка: старые сверху, готовые в конце.
- Карточка: стол или тип заказа (в зале/с собой/доставка/QR), таймер MM:SS, цветовой тон (работа/10 минут/20 минут/готово), прогресс «готово из всего», комментарий заказа, позиции с добавками, комментариями и пометкой «с собой».
- Действия: «Сделал» (ready), «Не сделал» (cooking), «Весь стол готов» (заказ ready, когда всё готово).
- Дозаказ приходит обновлением карточки; отдельной пометки нет.
- Звук: сигнал при новых заказах, тумблер в шапке.
- Связь: WebSocket + опрос каждые 5 с, реконнект через 3 с. При потере связи — индикатор Wi-Fi и экран «Сервер не отвечает» с кнопкой обновления; изменения без сервера не сохраняются.
- В шапке: ссылка «ТВ для гостей» (открывает гостевой экран филиала), полный экран, «Сменить повара», «Сменить организацию».

# 8. Экран раздачи (Expo)

Адрес: `https://admin.marjon.tech/expo`.

- Вход: телефон и пароль сотрудника с правом «Раздача» (`can_expo`).
- Список: заказы филиала, где все блюда готовы и выдача ещё не подтверждена.
- Карточка: номер, стол или тип, первые 5 блюд и «+N», возраст заказа в минутах, кнопка «Подтвердить — повар всё сделал».
- Подтверждение: `PATCH /kitchen/expo/orders/{id}/confirm` → карточка исчезает, заказ уходит на гостевой экран как «готов». Операция идемпотентна.
- Обновление: опрос каждые 4 с и при возврате на вкладку.
- Состояния ошибок: 401 — экран входа; 403 — «Нет доступа к раздаче»; 422 — «Экран не привязан к филиалу»; сеть — бейдж «Нет связи».

# 9. Гостевой ТВ-экран

Адрес: `https://admin.marjon.tech/tv?branch=<uuid>` (поддерживается `?b=`).

- Авторизация не нужна. Параметр филиала запоминается в браузере.
- Данные: `GET /kitchen/display?branch_id=…` — название компании, имя филиала, флаг включения и заказы `{номер, статус queued/ready, время}`. Обновление каждые 4 с; на экране только номер и статус — ни столов, ни сумм.
- Оформление: минималистичная белая шапка с логотипом и названием аккаунта, крупное время HH:MM, две колонки «в очереди» и «готово», угловой логотип. Заголовков колонок нет — колонки различаются цветом.
- Пагинация: если заказов больше, чем помещается, страницы листаются каждые 8 с, счётчик «1 / N».
- Состояния: экран выключен владельцем — «Экран выключен» (опрос продолжается); нет параметра филиала — «Экран ещё не настроен» с подсказкой; нет сети — бейдж «Нет связи — последние данные».
- Включение/выключение — только тумблером «Экран очереди» в настройках десктопа (флаг филиала `guest_display_enabled`).

# 15. Нефункциональные требования

## 15.1. Производительность

- Десктоп: отклик интерфейса без задержек на сенсорном терминале; фоновые операции (ящик, печать) не блокируют кнопки.
- Опрос KDS — 5 с, раздачи — 4 с, ТВ — 4 с; задержка появления нового заказа на кухне — до 5 с без учёта сети.
- Списки и отчёты рассчитаны на дневные объёмы заведения; тяжёлые выборки ограничены периодом и пагинацией.

## 15.2. Надёжность и восстановление

- Мультиэкранная работа не зависит от одного канала: сокеты дублируются опросом.
- При потере сети клиенты показывают последние данные и явный индикатор, а не пустой экран.
- Оплаты не проводятся офлайн — это защита от двойного списания.
- Бэкапы БД и файлов — на уровне инфраструктуры (PostgreSQL, MinIO); восстановление описано в `DEPLOY.md`.

## 15.3. Безопасность

- JWT HS256, access 15 минут, refresh 30 дней, области `app`/`hq_admin`/`kitchen`.
- Пароли и PIN — bcrypt; секреты шлюзов write-only.
- Rate limiting, CORS, блокировка после серии неудачных входов.
- Изоляция компаний и филиалов на уровне запросов; кухонная сессия ограничена белым списком.
- Аудит действий владельца; HQ-действия логируются отдельно.
- Публичный гостевой экран отдаёт только номера заказов, без персональных данных и сумм.

## 15.4. Совместимость

- Веб: актуальные Chrome, Edge, Safari; адаптивность панели от ноутбука до широкого монитора.
- Десктоп: Windows 10/11, разрешения от 1366×768, сенсорные и обычные мониторы.
- KDS/раздача: 1366×768 и выше, тёмная сцена для кухни.
- ТВ: 1280×720 и 1920×1080 проверены; вёрстка масштабируется от 32″ до 65″.
- Языки: русский, узбекский, английский.

## 15.5. Доступность и эргономика

- Крупные сенсорные цели на десктопе и KDS, контрастные статусы, звуковые сигналы.
- Отсутствие мелкого служебного текста на гостевом экране.
- Клавиатурный ввод PIN и поиска, подтверждение опасных действий.

- `postgres:16` — только localhost.
- `redis:7` — pub/sub для сокетов.
- `pgsty/silo` — объектное хранилище.
- `backend` — миграции Alembic при старте, uvicorn на 3 воркерах.
- Go-шлюзы Payme/Click/Uzum (порты 8001–8003).

## 16.3. Переменные окружения

`SECRET_KEY`, `DEBUG`, `ALLOWED_ORIGINS` (JSON-список), `POSTGRES_PASSWORD`, `MINIO_ROOT_PASSWORD`, `MINIO_PUBLIC_URL`, `WEBHOOK_SECRET`, `BACKEND_WORKERS`, `MASTER_PASSWORD` (сервисный доступ поддержки).

## 16.4. Миграции и релизы

- Alembic, около 100 ревизий; последние — `display01` (флаг гостевого экрана) и `expo01` (подтверждение раздачи).
- Порядок выката: сборка фронтенда → сборка десктопа → обновление манифеста магазина → бэкап БД → миграции → перезапуск сервисов → смоук-тест.
- Десктоп распространяется через `/store`; автообновления нет — пользователь скачивает новую версию.

- Проверка доступности доменов и TLS — на уровне nginx/certbot.

# 18. Ограничения и открытые зоны

Ниже — честный перечень того, что либо ограничено сознательно, либо ещё не доведено до конца. Это не ошибки документа, а фактическое состояние продукта на дату редакции.

**Продажи и касса**

1. Нет объединения и разделения счетов (split/merge) — в интерфейсе и API.
2. Частичные оплаты не поддерживаются: сумма должна совпадать с итогом. Смешанная оплата «наличные + карта» реализована в API, но в UI выбирается один способ.
3. Сервисный сбор рассчитывается автоматически и вручную не редактируется.
4. X-отчёта нет; Z-отчёт только печатный.
5. Скидка — только процентом на этапе оплаты; фиксированной суммы скидки в UI нет.

**Кухня и экраны**

6. KDS — одна доска без маршрутизации по станциям; API станций есть, но UI их не использует.
7. На KDS нет отдельной пометки «дозаказ» — приходит обновление карточки.
8. У гостевого экрана нет собственных настроек: включение только тумблером на десктопе.

**Веб-панель**

9. Раздел «Списание» и «Категории списания» в текущей сборке ограничены; перемещение между складами доступно только для просмотра.
10. Импорт приходов из Excel — заглушка; вкладка «Архив» документов отключена.
11. Матрица детальных доступов (50 модулей) отображается в карточке сотрудника, но на бэкенд не сохраняется — действуют роль и 16 тумблеров.
12. Раздел «Отзывы» — заглушка.
13. Z-отчёт на экране не показывает итоги, только параметры и печать.
14. Часть виджетов дашборда честно помечена «Скоро»/«Недоступно» до подключения контрактов (кредиторка/дебиторка, денежные расходы).

**HQ-админка**

15. Складские экраны HQ ждут контракта; дашборд частично на заглушках; «Marjon store» и «Языки» имеют расхождения маппинга полей.

**Офлайн и мобильное**

16. Офлайн-очередь ограничена сменами статусов; оплаты офлайн не проводятся; серверный обработчик `OfflineJob` не запущен.
17. Мобильное приложение собрано, но публикация в Google Play/App Store и мобильные сборки в магазине отсутствуют — в `/store` только Windows.

**Инфраструктура**

18. Автообновления десктопа нет; новая версия скачивается вручную из магазина.

- [ ] Вход владельца, восстановление сессии, выход.
- [ ] Дашборд: KPI, график, складской виджет, топ блюд, последние заказы.

- [ ] 9 разделов настроек сохраняют данные.

- [ ] Подключение к серверу, вход моноблока, PIN, смена режима.

- [ ] Вход моноблок → повар → PIN; выбор филиала при необходимости.
