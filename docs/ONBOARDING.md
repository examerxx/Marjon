# 1. Что за продукт

**Marjon Restaurant OS** — облачная SaaS-платформа для автоматизации ресторанов,
кафе и фаст-фуда в Узбекистане. Одна компания может иметь несколько филиалов;
все данные изолированы по компании и филиалу.

Система закрывает полный цикл:

- приём заказа (зал, самовывоз, доставка, QR);
- кухню (KDS), раздачу (Expo) и гостевой ТВ-экран;
- оплату (наличные, карта, Payme, Click, Uzum, бонусы, долг);
- склад (приход, остатки, тех-карты, инвентаризация, списания, отходы);
- финансы (кассы, операции, категории, контрагенты);
- персонал (роли, права, смены, посещаемость, история входов);
- отчёты, Z-отчёт, аналитику;
- CRM, лояльность, доставку, уведомления, фискализацию (интеграция готова
  архитектурно, провайдер ОФД пока не подключён).

## Каналы

| Канал | Кто пользуется | Код | Адрес в проде |
|-------|----------------|-----|---------------|
| Веб-панель владельца | владелец | `frontend/` (`index.html`) | `admin.marjon.tech` |
| POS-десктоп | кассир, официант, курьер | `desktop/` | устанавливается с `/store` |
| Кухонный экран (KDS) | повара | `frontend/` (`kitchen.html`) | `kitchen.marjon.tech` |
| Экран раздачи (Expo) | менеджер раздачи | `frontend/` (`expo.html`) | `admin.marjon.tech/expo` |
| Гостевой ТВ | посетители | `frontend/` (`tv.html`) | `admin.marjon.tech/tv?branch=<uuid>` |
| Мобильный клиент | персонал | `mobile/` (Flutter) | не опубликован |
| HQ-админка | супер-админ Marjon | `frontend/src/admin/` | `admin.marjon.tech/<секретный путь>` |
| Сайт | клиенты | `landing/` | `marjon.tech` |

## Что уже в проде

- Бэкенд, веб-панель, десктоп, KDS, Expo и ТВ работают на реальных клиентах.
- Десктоп поставляется как Windows-установщик и portable-сборка через `/store`
  (версия 1.0.6 на дату редакции), автообновления нет.
- Мобильное приложение собрано, но в магазины не публиковалось.
- `owner/` — отдельное Flutter-приложение владельца; в поставку не входит и не
  поддерживается. Не тратьте на него время, если задача не про него.

## Прод в двух словах

Один сервер, Docker Compose в `/home/ubuntu/marjon`. Внутри: PostgreSQL 16,
Redis 7, объектное хранилище, backend (запускает `alembic upgrade head` при
старте), Go-шлюзы платежей, nginx с TLS и статикой. Подробности и порядок
выката — [../DEPLOY.md](../DEPLOY.md).

**Правило по умолчанию: прод — read-only.** Любое изменение на сервере — только
по явной просьбе владельца. `docker compose down -v` не выполняется никогда:
это уничтожает тома с базой.

# 4. Стек и принципы

| Слой | Технологии |
|------|-----------|
| Бэкенд | Python 3.13, FastAPI, SQLAlchemy 2.0 async, Alembic, Pydantic v2, JWT HS256, slowapi, bcrypt |
| БД | PostgreSQL 16 (прод), SQLite (разработка и часть тестов) |
| Шина | Redis 7 pub/sub для WebSocket (кухня, печать) |
| Файлы | MinIO-совместимое хранилище; в dev — `backend/media` |
| Веб | React 18, JSX, Vite 5, React Router 6, Chart.js, i18next |
| Десктоп | Electron 28 + React, electron-vite, electron-builder |
| Мобильный | Flutter 3.7+ |
| Платежи | Go-микросервисы с вебхуками в backend |
| Инфраструктура | Docker Compose, nginx, certbot |

## Принципы, которые нельзя нарушать

- **Веб — JavaScript/JSX, не TypeScript.** Новый `.ts/.tsx` не добавляем.
- **CSS только через токены** `marjon-tokens.css` (`--mj-*`). Никаких Tailwind и
  произвольных hex-цветов в новых компонентах.
- **Мультитенантность.** Любая бизнес-сущность привязана к `company_id`,
  операционная — ещё и к `branch_id`. Фильтрация по филиалу обязательна.
- **Права проверяются на бэкенде**, а не только скрытием кнопок в UI.
- **Деньги** — только через сервисный слой, с проверкой суммы и идемпотентности.
- **Миграции** после применения не редактируются: создаётся новая ревизия.
- **Секреты** не попадают в git, URL и командную строку.

# 6. Запуск локально

## 6.1. Бэкенд

```bash
cd backend
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/macOS:
source .venv/bin/activate

pip install -r requirements.txt
```

Запуск на SQLite (быстрый путь):

```bash
# из каталога backend/
DATABASE_URL="sqlite+aiosqlite:///./app.db" python devrun.py
```

- `devrun.py` создаёт таблицы по моделям и поднимает uvicorn на
  `127.0.0.1:8000`.
- Внутри `devrun.py` уже задан фиксированный dev-`SECRET_KEY`, поэтому
  перезапуск сервера не разлогинивает клиентов.
- Если не передать `DATABASE_URL`, скрипт подставит путь-заглушку
  `/agent/workspace/...` — всегда передавайте переменную явно.
- Swagger: http://localhost:8000/docs · health: http://localhost:8000/health

Демо-данные:

```bash
python seed.py                      # компания, филиалы, сотрудники, меню
python scripts/seed_owner_login.py  # владелец для десктопа
python scripts/seed_waiter_login.py # официант
```

Если нужен PostgreSQL, поднимите его через Docker Compose (`docker compose up -d db`)
и задайте `DATABASE_URL=postgresql+asyncpg://...`.

## 6.2. Веб-панель

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173
```

- Скрипт жёстко занимает порт 5173 (`--strictPort`). Если порт занят:
  `npx vite --host localhost --port 5175 --strictPort`.
- Dev-режим читает `frontend/.env.development` (`VITE_API_URL=/api/v1`) и ходит
  через прокси Vite на `http://localhost:8000`. Бэкенд должен быть запущен.
- Прод-сборка читает `frontend/.env.production` (`https://api.marjon.tech`).
  Этот файл лежит в git специально: без него сборка молча зашивает localhost.

Адреса приложений в dev:

| Приложение | URL |
|------------|-----|
| Панель владельца | `http://localhost:5173/` |
| HQ-админка | `http://localhost:5173/admin.html` |
| KDS | `http://localhost:5173/kitchen.html` |
| Expo | `http://localhost:5173/expo.html` |
| ТВ | `http://localhost:5173/tv.html?branch=<UUID филиала>` |

## 6.3. POS-десктоп

```bash
cd desktop
npm install
npm run dev        # renderer на http://localhost:5174
```

- `npm run dev` использует `scripts/dev.js`, который удаляет переменную
  `ELECTRON_RUN_AS_NODE` — иначе Electron запускается как Node и окно не
  открывается.
- Порт renderer — 5174, слушает только `localhost`.
- Адрес сервера задаётся в самом приложении при первом запуске и хранится в
  `localStorage.marjon_server_url`. Для локальной работы укажите
  `http://127.0.0.1:8000/api/v1`.
- Main-процесс дополнительно поднимает LAN-прокси `:8765`, чтобы мобильные
  устройства в той же сети могли ходить в API через кассу.
- В dev-режиме удобно подключаться по CDP к `127.0.0.1:9222` (нужен запуск с
  `--remote-debugging-port=9222`).

## 6.4. Мобильный клиент

```bash
cd mobile
flutter pub get
flutter run
```

Приложение повторяет сценарии десктопа: подключение к серверу, вход сотрудника,
режимы касса/кухня, зал, сборка заказа, оплата, панели истории и финансов.

## 6.5. Полный стек через Docker

Для проверки «как на проде» удобнее Docker. Готовая инструкция:
[TESTING_WINDOWS.md](TESTING_WINDOWS.md). Кратко:

```bash
docker compose up -d --build
```

Compose поднимает PostgreSQL, Redis, хранилище, backend (с миграциями), шлюзы и
nginx. Для локальной разработки с горячей перезагрузкой всё же удобнее
запускать backend и frontend отдельно (разделы 6.1–6.2).

# 7. Демо-данные и входы

Все логины ниже — **только для локальной dev-базы**, создаются seed-скриптами.
На проде эти учётки отсутствуют.

| Кто | Логин | Пароль | Откуда |
|-----|-------|--------|--------|
| Владелец (веб) | `+998901234567` | `Admin1234` | `seed.py` |
| Кассир | `+998901234568` | `Staff1234` | `seed.py` |
| Официант | `+998901234569` | `Staff1234` | `seed.py` |
| Повар | `+998901234570` | `Staff1234` | `seed.py` |
| Владелец (десктоп) | `+998998900000` | `owner123` | `scripts/seed_owner_login.py` |
| Официант (десктоп) | `+998900078779` | `102938` | `scripts/seed_waiter_login.py` |

Пароли и телефоны всегда сверяйте с константами в самом скрипте: seed-файлы —
источник истины, а не таблица выше.

**Порядок первого входа в десктоп:**

1. Указать адрес сервера (`http://127.0.0.1:8000/api/v1`).
2. Войти моноблоком (телефон + пароль).
3. Выбрать сотрудника и ввести PIN. PIN задаёт владелец в веб-панели
   (Настройки → Сотрудники); в исходниках его нет.
4. Если смена закрыта — приложение предложит открыть смену.

**Как включить KDS и ТВ:**

- Сотруднику-моноблоку нужно право `can_kitchen` (или вход по логину филиала).
  На KDS: привязка устройства → выбор повара → PIN.
- Для экрана раздачи нужно право `can_expo`; вход — телефон + пароль.
- Гостевой ТВ включается тумблером «Экран очереди» в настройках десктопа
  (`branch.guest_display_enabled`). Публичный URL:
  `/tv.html?branch=<UUID>` (именно `branch`, не `branch_id`).

# 8. Роли и доступ

Канонические роли компании (`backend/app/modules/rbac/constants.py`):

| Слаг | Роль | Где работает |
|------|------|--------------|
| `owner` | Владелец | веб-панель, десктоп |
| `manager` | Менеджер | веб-панель, POS |
| `cashier` | Кассир | POS-десктоп |
| `waiter` | Официант | POS-десктоп |
| `monoblock` | Терминал | POS-десктоп, KDS |
| `kitchen` | Повар | KDS |
| `courier` | Курьер | POS-десктоп (режим «Курьер») |
| `warehouse` | Завсклад | веб-панель, склад |

Платформенные роли: `superadmin` и `hq_admin` (HQ-админка, отдельный вход
`/auth/admin/login` и отдельный scope токена).

Важные правила:

- В веб-панель пускается **только `owner`**. Остальные работают через десктоп/KDS.
- Роль `admin` — историческая, прав не даёт.
- 40 разрешений RBAC (`module:action` + область `self`/`branch`/`company`) —
  каталог в `backend/app/modules/rbac/permissions.py`.
- У сотрудника дополнительно 16 персональных тумблеров (`can_kitchen`,
  `can_expo`, `can_close_bill`, …) — они хранятся в карточке сотрудника и
  проверяются на бэкенде.
- Матрица «50 модулей» в карточке сотрудника — **только UI**, на бэкенд не
  сохраняется. Не пытайтесь искать её в БД.

# 9. Бэкенд: модули

```

Точка сборки приложения — `backend/app/main.py`. Реестр всех моделей —

# 10. Ключевые бизнес-процессы

Подробно — ТЗ v3, глава 4. Здесь — минимум, чтобы понимать код.

## Заказ

- Статусы: `new → accepted → cooking → ready → completed`, отмена — `cancelled`.
- Статусы позиции: `pending → cooking → ready → served`, отмена — `cancelled`.
- Переходы валидируются `VALID_TRANSITIONS` / `ITEM_TRANSITIONS` в
  `pos/service.py`. Не добавляйте переход «напрямую» в роутере.
- Номера: публичный ID с 10 000 000; внутренний номер уникален в пределах
  компании/филиала/операционного дня (`day_start_hour`).
- Завершённый заказ нельзя менять без переоткрытия (`reopen` возвращает
  `completed → accepted`).
- Отмена требует причину, а при настроенном пароле отмены — ещё и пароль.

## Дозаказ

При добавлении блюд в уже отправленный заказ кухня получает тикет **только с
новыми позициями**; кассир видит полный счёт. Это осознанное поведение, не
баг — не «исправляйте» его.

## Оплата

- Методы: наличные, карта, Payme, Click, Uzum, бонусы, долг.
- Сумма оплаты должна совпадать с итогом; частичных оплат нет.
- Картой нельзя переплатить; наличными можно (возврат сдачи).
- Разделения и объединения счетов нет.
- Долг оформляется через контрагента и недоступен официанту.
- Повторная отправка защищена ключом идемпотентности.

## Смена и Z-отчёт

- Смена кассира: открыть → работать → закрыть; начальная и конечная наличность.
- Z-отчёт строится в `analytics` и печатается через `printers`. X-отчёта нет.

## Склад

- Приход применяется к остаткам при сохранении документа.
- Партии списываются по FIFO.
- Продажа автоматически списывает сырьё по тех-картам (идемпотентно по паре
  «ингредиент + склад»).
- Инвентаризация создаёт приход/расход по расхождениям.
- Перемещение между складами — только шапка документа.
- Списание не влияет на остатки; отходы учитываются отдельно.

## Печать

- Принтер — сетевой, ESC/POS, TCP 9100.
- Задания создаются в БД, десктоп забирает их по WebSocket
  `/printers/ws/{branch_id}` и подтверждает `done`/`fail`.
- Шаблоны чека и кухонного чека настраиваются в компании.

# 11. База данных и миграции

- Prod: PostgreSQL 16. Dev: SQLite.
- Alembic: `backend/migrations/versions/`, 100 ревизий.
- Прод применяет миграции автоматически при старте контейнера
  (`alembic upgrade head`).

Правила:

1. Новая схема = новая ревизия Alembic. Применённые ревизии не редактируются.
2. Новая модель регистрируется в `models_registry.py`.
3. Перед экспериментами с локальной БД делайте бэкап `app.db`.
4. Локальная SQLite-база, созданная через `create_all`, может не иметь
   `alembic_version`. Не запускайте на ней `alembic upgrade head` вслепую —
   Alembic попытается создать всю схему заново. Либо ставьте baseline
   (`alembic stamp head`), либо применяйте только DDL новой миграции.

Основные сущности: `Company`, `Branch`, `User`, `Order`, `OrderItem`,
`Payment`, `CashierShift`, `Product`, `Ingredient`, `StockBatch`,
`StockMovement`, `Purchase`/`Transfer`/`InventoryCheck`/`Expense`/`Waste`,
`Hall`/`Table`, `Counterparty`, `FinancialOperation`, `Printer`/`PrintJob`,
`Receipt`/`FiscalOutbox`, `Customer`, `Employee`. Полная таблица — ТЗ §13.

# 12. API и реальное время

- Префикс `/api/v1`, OpenAPI — http://localhost:8000/docs.
- Авторизация: `Authorization: Bearer <access_token>`.
- Токен несёт scope (`app`, `hq_admin`, `kitchen`) и версию авторизации.
- Ошибки — стандартный FastAPI `detail`; фронтенд показывает его пользователю.
- Rate limiting: логин 5/мин, регистрация 5/мин, админ-логин 10/мин, refresh 30/мин.
- CORS — только явный список origin, wildcard отбрасывается.

WebSocket:

| Канал | URL | События |
|-------|-----|---------|
| Кухня | `/ws/kitchen?token=…&branch_id=…` | `new_order`, `order_updated`, `order_cancelled`, `item_status_changed`, `order_completed` |
| Печать | `/printers/ws/{branch_id}` | задания печати |

Клиенты дублируют сокет опросом (KDS — 5 с, раздача — 4 с, ТВ — 4 с), поэтому
потеря соединения не останавливает работу.

Ключевые группы эндпоинтов: `/auth`, `/pos`, `/payments`, `/kitchen`,
`/inventory`, `/warehouse`, `/finance`, `/analytics`, `/reports`, `/hr`,
`/printers`, `/fiscal`, `/crm`, `/delivery`, `/loyalty`, `/rbac`, `/companies`.
Полный список — ТЗ §14 или Swagger.

```

- Перед сборкой релиза проверьте `desktop/.env.development` /

- Бинарники в git не кладутся (`store-files/*.exe` в `.gitignore`). В репозитории
  обновляется только `store-files/manifest.json` (версия, размеры, sha256).
- Автообновления нет: клиент скачивает новую версию со страницы `/store`.

## Прод

Полный порядок — [../DEPLOY.md](../DEPLOY.md). Схема:

1. Бэкап БД (`pg_dump | gzip`) и текущего `frontend/dist`.
2. На сервере: `git fetch origin main && git reset --hard origin/main`.
3. `docker compose build backend && docker compose up -d backend`
   (миграции применяются в контейнере при старте).
4. Собранный локально `dist` распаковать во временный каталог и
   `rsync -a --delete` в `frontend/dist/` (каталог не переименовывать — он
   bind-mount).
5. Проверить `alembic current`, `/health`, хэши статики и публичные URL.

Запреты:

- не выполнять `docker compose down -v`;
- не править прод `.env` без явного разрешения;
- не вставлять пароли/токены в команды, URL и файлы;
- не деплоить «заодно» с задачей, если об этом не просили.

# 16. Правила работы с кодом

- Ветка на задачу: `feat/...`, `fix/...`; вливание в `main` через PR.
- Коммиты — conventional-стиль с русским описанием:
  `fix(pos): сотрудник с PIN важнее владельца на терминале`,
  `feat(kitchen,expo,tv): …`.
- Не добавляйте зависимости без необходимости. Сначала проверьте, есть ли
  решение на текущем стеке.
- Не тащите TypeScript, Tailwind и новые UI-библиотеки.
- CSS: правьте файл, где уже живёт правило, а не накрывайте оверрайдом.
- i18n: новые строки — через `t()`, ключи в `ru.json`/`uz.json`/`en.json`;
  `t()` понимает и русский текст (обратный индекс), но новые ключи лучше
  добавлять явно.
- Комментарии — только про «почему», не про «что»; не описывайте очевидное.
- Не расширяйте скоуп задачи: отдельный багфикс не требует рефакторинга вокруг.
- Деньги и склад — только через сервисный слой, с транзакцией и идемпотентностью.
- Любое изменение прав доступа согласуйте: RBAC влияет на всех клиентов.

# 17. Известные ограничения

Это фактическое состояние, а не список багов. Подробно — ТЗ §18.

**Касса:** нет split/merge счетов; частичных оплат нет; смешанная оплата есть в
API, но не в UI; скидка только процентом; X-отчёта нет.

**Кухня:** одна доска без маршрутизации по станциям; отдельной пометки
«дозаказ» нет — приходит обновление карточки; у ТВ нет своих настроек, только
тумблер на десктопе.

**Веб:** перемещение между складами только для просмотра; импорт приходов из
Excel — заглушка; матрица 50 модулей не сохраняется; «Отзывы» — заглушка;
Z-отчёт на экране показывает параметры и печать, но не итоги; часть виджетов
дашборда помечена «Скоро».

**HQ:** складские экраны ждут контракта, дашборд частично на заглушках.

**Офлайн/мобилка:** офлайн-очередь только для статусов; оплаты офлайн нельзя;
`OfflineJob` не обрабатывается; мобильное приложение не опубликовано.

**Инфраструктура:** автообновления десктопа нет; фискальный провайдер не
подключён (`fiscal_enabled=False`).

# 18. Типовые проблемы

| Симптом | Причина | Что делать |
|---------|---------|------------|
| Порт 5173 занят | `vite --strictPort` | `npx vite --host localhost --port 5175 --strictPort` |
| Веб не видит API | backend не запущен или не на 8000 | поднять `devrun.py`, проверить прокси Vite |
| Прод-сборка молча не логинит | нет `VITE_API_URL` | проверить `frontend/.env.production` перед сборкой |
| Десктоп-релиз не логинит клиентов | собран с локальным `VITE_DEFAULT_SERVER_URL` | пересобрать с прод-адресом |
| ТВ показывает «Экран ещё не настроен» | передан `?branch_id=` | передать `?branch=<UUID>` и включить тумблер на десктопе |
| `alembic upgrade head` падает на dev | SQLite создана через `create_all`, нет `alembic_version` | бэкап + `alembic stamp head` или применить только DDL новой ревизии |
| CORS-ошибка на новом порту | origin не в `ALLOWED_ORIGINS` | добавить origin в конфиг backend |
| Electron-окно не открывается | унаследован `ELECTRON_RUN_AS_NODE` | запускать через `npm run dev` (скрипт чистит переменную) |
| 401 после перезапуска backend | сменился `SECRET_KEY` | `devrun.py` использует фиксированный ключ; при своём ключе — войти заново |
| KDS пустой | у моноблока нет `can_kitchen` или не выбрана смена | выдать право в карточке сотрудника, открыть смену |
| Тест падает только в полном прогоне | общий параллельный запуск/флаки | прогнать файл отдельно, сверить с CI |

# 21. Глоссарий

| Термин | Значение |
|--------|----------|
| **Компания** | Клиент SaaS (ресторан/сеть). Верхний уровень изоляции данных. |
| **Филиал** | Точка компании: свой зал, касса, кухня, склад, сотрудники. |
| **Моноблок** | Терминал в зале; сотрудник с ролью `monoblock`, вход телефон + PIN. |
| **Дозаказ** | Добавление блюд в уже отправленный заказ; кухня получает только новые позиции. |
| **Раздача (Expo)** | Экран, где готовые блюда подтверждают и выдают; только после подтверждения заказ попадает на ТВ. |
| **KDS** | Kitchen Display System — кухонный экран с заказами и статусами. |
| **Тех-карта** | Нормы расхода сырья на блюдо; основа автосписания со склада. |
| **Партия (batch)** | Приход сырья с количеством и сроком; списывается по FIFO. |
| **Z-отчёт** | Итоговый отчёт за смену/день, печатается на кассе. |
| **Смена** | Рабочий период кассира/сотрудника с открытием и закрытием. |
| **ОФД / ЦОТУ** | Оператор фискальных данных Узбекистана; интеграция подготовлена, провайдер не подключён. |
| **HQ** | Headquarters — админка платформы Marjon для супер-админа. |
| **Тумблер** | Персональное право сотрудника (16 штук), выдаётся в карточке. |
| **Тенант** | Компания-клиент в мультитенантной архитектуре. |
